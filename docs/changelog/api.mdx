Polar uses date-based API versions to evolve the API without unexpectedly changing
the contract your integration depends on. Versions use the `YYYY-MM` format, such
as `2026-10`, and apply to API requests, responses, webhook payloads, and SDK types. [Read more](/api-reference/current/versioning)

<Update label="2027-01">

**This will become the Current version on January 1, 2027.**

### Breaking changes

These changes only apply once you upgrade to `2027-01`. Earlier API versions keep the previous behavior.

#### Removed fields

Removed the following obsolete fields, including fields that were already hidden from the API documentation and SDKs. Response field removals also apply to webhook payloads.

- Fixed discounts: removed `amount` and `currency` from create and update requests, responses, and webhook payloads. Use `amounts` instead; it is required when creating a fixed discount. Removed input fields are ignored.
- Organization onboarding details: removed `about`, `intended_use`, `customer_acquisition`, `future_annual_revenue`, and `previous_annual_revenue` from create/update requests and KYC responses. Removed input fields are ignored. Updating details replaces stored values with the remaining supported fields.
- Orders: `user_id`, `user`, `product_price_id`, `product_price`, `amount` (use `net_amount`), and `from_balance_amount` (use `applied_balance_amount`). Embedded subscriptions also lose `user_id`.
- Subscriptions: `user_id`, `user`, `price_id`, and `price`. Use `customer_id`, `customer`, and `prices` instead.
- Customer state active subscriptions: `price_id`. Use `prices` instead.
- Customer portal orders and subscriptions: `user_id`, order `product_price_id` and `product_price`, and subscription `price_id` and `price`.
- License keys: `user_id` and `user`. Use `customer_id` and `customer` instead.
- Benefit grants: `user_id`. Use `customer_id` instead.
- Checkout links: `product_id`, `product_price_id`, `product`, and `product_price`. Use `products` instead.
- Checkouts: `customer_external_id` (use `external_customer_id`), `customer_billing_address_fields` (use `billing_address_fields`), and `subtotal_amount` (use `net_amount`).
- Checkouts: `product_price_id` from responses and from update and client update requests. Creating a checkout session from a single `product_id` or `product_price_id` is no longer supported; use `products` or `external_products` instead.
- Checkout links: creating a checkout link from a single `product_id` or `product_price_id` is no longer supported. Use `products` instead.
- Products: `recurring_interval` and `recurring_interval_count` from update requests. They could only be set on legacy recurring products.
- Seat-based prices: `seat_tiers` is replaced by `tiers`, with the purchasable seat range in `minimum_units` and `maximum_units`. Create requests accept `tiers` and an optional `minimum_units`.
- Organizations: `bio`, `company`, `blog`, `location`, `twitter_username`, `pledge_minimum_amount`, `pledge_badge_show_amount`, `default_upfront_split_to_contributors`, and `notification_settings`.
- Organizations embedded in other resources: `email`, `website`, `socials`, `status`, `details_submitted_at`, `feature_settings`, `subscription_settings`, and `customer_email_settings`.
- Custom and Slack shared channel benefits: `is_tax_applicable`.
- Discord benefit properties: `guild_token`. Use `guild_id` instead.
- GitHub repository benefit properties: `repository_id`. Use `repository_owner` and `repository_name` instead.
- Legacy recurring prices: the `LegacyRecurringProductPrice` schema is dropped from the price union, and the deprecated `type` and `recurring_interval` fields are removed from price responses. Earlier API versions retain them.

#### Stricter requests

- Update requests reject `null` for fields that can't be cleared, with a `422` error. Earlier versions treat an explicit `null` on those fields as if the field were omitted. Omit the field instead to keep its current value.
- Ingesting events requires an organization access token or an OAuth token scoped to a single organization. Other tokens get a `403` error.

#### New values in responses

Clients that only accept a fixed set of values should handle these:

- Organization `proration_behavior` and subscription settings `proration_behavior` can return `auto`.
- The events list can return the new `benefit.manually_granted`, `benefit.manually_revoked`, and `benefit.unrevoked` system events.
- `meter.credited` event metadata includes a `reason` (`benefit` or `manual`).

### New endpoints

- Benefit grants: `POST /v1/benefit-grants/` grants a benefit manually to a customer or one of their members, using either Polar IDs or external IDs. `DELETE /v1/benefit-grants/{id}` revokes a grant manually, including grants from purchases. `PATCH /v1/benefit-grants/{id}` undoes a manual revocation by setting `manually_revoked_at` to `null`.
- Customer meter credits: `POST /v1/customer-meters/credits` grants credits on a customer meter manually and returns the `meter.credited` event. `POST /v1/customer-meters/credits/{id}/reverse` reverses a manual credit, once per credit, within 7 days and in the current billing period.
- `GET /v1/meters/external/{external_id}` and `GET /v1/webhooks/endpoints/external/{external_id}` get a meter or webhook endpoint by external ID.

### External IDs

- Products, benefits, discounts, meters, and webhook endpoints have an `external_id` field. Set it on create and update requests; it must start with a letter or digit and contain only letters, digits, `_`, `-`, `.` and `:`.
- New `external_id` filter on the list products, benefits, discounts, and meters endpoints.
- New `external_product_id` filter on the list checkouts, orders, order export, subscriptions, and metrics endpoints, and `external_meter_id` on the list customer meters endpoint.
- New `external_benefit_id`, `member_id`, and `external_member_id` filters on the list benefit grants endpoint.
- Checkout sessions can be created from `external_products`, a list of product external IDs, instead of `products`.

### Other additions

- Webhook payloads include an `event_id`. Use it to discard duplicate deliveries.
- New `format` filter on the list webhook endpoints endpoint. `2027-01` can be selected as a webhook endpoint `api_version`.
- Benefit grants (including customer portal grants and benefit grant webhook payloads) include `manually_granted_at` and `manually_revoked_at`.
- Products, benefits, meters, and custom fields include `catalog_id` and `is_current`, and their list endpoints accept `catalog_id` and `catalog_status` filters.
- Recurring products have a `trial_payment_setup_required` setting, available on create, update, and responses (including checkout links). When `false`, customers can start a trial without setting up a payment method.
- Creating a subscription accepts a `currency`.
- Subscription `pending_update` includes `discount_id` and `discount_unset`.
- License keys include `order_id`, `order`, `subscription_id`, and `subscription` when they were granted from a purchase.
- Public checkout responses include `payment_method_types`.
- New `created_after` and `created_before` filters on the list checkouts endpoint.
- Customer portal: subscriptions include `payment_method_id`, and a subscription whose trial ended without converting can be reactivated with `{"reactivate": true}`.
- Subscription update requests accept `auto` as `proration_behavior`, which applies upgrades immediately and schedules downgrades. [Read more](/features/subscriptions/proration)
- Subscription `started_at` is no longer nullable.

</Update>

- Removed the `secret` parameter when [creating](/api-reference/2026-10/webhooks/create-webhook-endpoint) or [updating](/api-reference/2026-10/webhooks/update-webhook-endpoint) webhook endpoints. New endpoint secrets are generated by Polar.

<Update label="2026-04">

### Standard Webhooks signing

New webhook endpoints with secrets generated by Polar on or after **September 8,
2026 at 00:00 UTC** use signing compliant with the Standard Webhooks specification.

Endpoints with secrets generated before this cutoff continue to use Polar's
previous signing approach, preserving compatibility with existing integrations.
Endpoints with user-provided secrets also retain the previous approach.
We will continue to support this approach for as long as necessary; there is no
required migration deadline.

To adopt Standard Webhooks signing for an existing endpoint, **regenerate its
secret** and update your webhook handler to use the new secret. When using a
Standard Webhooks library directly, pass the new secret as-is, without
Base64-encoding it first.

See [webhook signature validation](/integrate/webhooks/delivery#custom-validation)
for details on both signing approaches.

</Update>
