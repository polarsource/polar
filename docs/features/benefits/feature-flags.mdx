A **Feature Flag benefit** is an entitlement your application checks. Polar grants it when a customer buys a product that includes it and revokes it when access ends. Your code decides what the flag unlocks.

Use it to gate premium features, give beta access, or set plan limits through metadata, without checking product IDs in your code.

## What the customer gets

Access to whatever your application unlocks for the flag. Polar delivers nothing on its own, and the flag is hidden from the customer by default.

## Create it

A feature flag has no properties. Configure it through `metadata`, which your application reads back with the grant.

<Tabs>
  <Tab title="Dashboard">
    - Open **Products** → **Benefits**
    - Click **Create Benefit**
    - Choose **Feature Flag** as the **Type**
    - Set the **Description**, e.g. "Pro features"
    - Optionally click **Add Metadata** and add keys such as `tier` → `pro`
    - Click **Create**
  </Tab>
  <Tab title="CLI">
    ```bash
    polar benefits create --data '{
      "type": "feature_flag",
      "description": "Pro features",
      "properties": {},
      "metadata": { "tier": "pro", "max_projects": 10 }
    }'
    ```

    See [`polar benefits`](/integrate/cli/reference/benefits).
  </Tab>
  <Tab title="Prompt">
    ```text Prompt
    Create a Feature Flag benefit called "Pro features" with metadata tier=pro and max_projects=10 in my Polar sandbox organization.
    ```

    Uses the `benefits_create` operation of the [Polar MCP server](/integrate/mcp).
  </Tab>
</Tabs>

Then attach it to a product. See [Manage benefits](/features/benefits/introduction#attach-a-benefit-to-a-product).

## Options

| Dashboard | API property | Default |
| --- | --- | --- |
| **Metadata** | `metadata` | None |
| **Visibility** | `visibility` | **Hidden** (`private`) |

`properties` is always an empty object.

## Check access in your application

Read the customer's `granted_benefits` from the [customer state](/integrate/customer-state) by your own user ID. Match on the benefit's `id`, or read `benefit_metadata` for its configuration. These examples use API version `2026-10`.

<CodeGroup>
```typescript TypeScript
const state = await polar.customers.getStateExternal("user_123");

const pro = state.granted_benefits.find(
  (grant) => grant.benefit_id === process.env.PRO_FEATURES_BENEFIT_ID,
);
const hasPro = pro !== undefined;
const maxProjects = Number(pro?.benefit_metadata.max_projects ?? 1);
```

```python Python
import os

state = polar.customers.get_state_external("user_123")

pro = next(
    (g for g in state.granted_benefits if g.benefit_id == os.environ["PRO_FEATURES_BENEFIT_ID"]),
    None,
)
has_pro = pro is not None
max_projects = int(pro.benefit_metadata.get("max_projects", 1)) if pro else 1
```

```bash cURL
curl -s https://sandbox-api.polar.sh/v1/customers/external/user_123/state \
  -H "Authorization: Bearer $POLAR_ACCESS_TOKEN" \
  -H "Polar-Version: 2026-10" \
  | jq '.granted_benefits[] | select(.benefit_id == "'"$BENEFIT_ID"'")'
```
</CodeGroup>

From your terminal: `polar customers get_state_external user_123`, or ask your agent "Does user_123 have the Pro features benefit in my Polar sandbox organization?" (the `customers_get_state_external` operation).

Don't call the API on every request. Cache the result and refresh it when the `customer.state_changed` webhook arrives. Its payload is the same customer state. See [Sync customer state](/quickstart/webhooks).

## Customer experience

Nothing changes for the customer in Polar. Hidden by default, the flag doesn't appear at checkout, in emails or in the [Customer Portal](/features/customer-portal/introduction). They see the feature in your application.

## Revocation

- **Subscriptions:** granted while the subscription is `active` or `trialing`, including after the customer cancels, until the period ends. Revoked when the subscription ends.
- **One-time purchases:** granted for good, unless you revoke it when refunding the order.

On revocation, the grant disappears from `granted_benefits` and Polar sends `customer.state_changed`.

## Visibility

Configurable, and hidden (`private`) by default. Set it to **Visible** if you want the flag's description listed on the product and in the Customer Portal. Hidden flags are still in the customer state.

<Visibility for="agents">
  Rules for integrating feature flags:
  - Key the customer by your app's user ID as `external_id`, and read `GET /v1/customers/external/{external_id}/state`. Never read it with a token in client-side code.
  - Grant access when `granted_benefits` contains an entry whose `benefit_id` equals the feature flag benefit's ID. Store that ID in configuration; don't match on `description`.
  - Revoke access when the entry is gone. Don't compare subscription status yourself: Polar already keeps `granted_benefits` in sync with `active`/`trialing` subscriptions.
  - Keep a cached copy and update it from the `customer.state_changed` webhook, verifying the signature.
  - Create the benefit with `type: "feature_flag"`, `properties: {}`, and configuration in `metadata` (values are strings, integers, numbers or booleans).
</Visibility>
