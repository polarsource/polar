A **benefit** is what a customer receives when they buy a product: a license key, a file, a Discord role, credits on a meter. You create a benefit once and attach it to any number of products. Polar grants it on purchase and revokes it when access ends. See [Benefits](/concepts/benefits) for grants and their lifecycle.

This page covers the tasks every benefit type shares. Code examples use API version `2026-10`.

## Benefit types

| Type | API `type` | What the customer gets |
| --- | --- | --- |
| [Feature Flag](/features/benefits/feature-flags) | `feature_flag` | A flag, with metadata, that your application checks |
| [Meter Credits](/features/usage-based-billing/credits) | `meter_credit` | Units credited to a meter balance |
| [License Keys](/features/benefits/license-keys) | `license_keys` | A unique key, with optional expiry, activations and usage limit |
| [File Downloads](/features/benefits/file-downloads) | `downloadables` | Files to download |
| [GitHub Repository Access](/features/benefits/github-access) | `github_repository` | An invitation to a private repository |
| [Discord Invite](/features/benefits/discord-access) | `discord` | An invitation to a Discord server, with a role |
| [Shared Slack Channel](/features/benefits/slack-shared-channel) | `slack_shared_channel` | A Slack Connect channel with your team |
| [Custom](/features/benefits/custom) | `custom` | A private note, for anything else you deliver |

## Create a benefit

Every benefit has a `type`, a `description` of 3 to 42 characters, and `properties` that depend on the type. The description is what customers see on the product, at checkout and in the [Customer Portal](/features/customer-portal/introduction).

<Tabs>
  <Tab title="Dashboard">
    - Open **Products** → **Benefits**
    - Click **Create Benefit**
    - Pick a **Type** and fill in the **Description**
    - Fill in the type's options and click **Create**
  </Tab>
  <Tab title="CLI">
    ```bash
    polar benefits create --data '{
      "type": "feature_flag",
      "description": "Beta access",
      "properties": {}
    }'
    ```

    See [`polar benefits`](/integrate/cli/reference/benefits).
  </Tab>
  <Tab title="Prompt">
    ```text Prompt
    Create a Feature Flag benefit called "Beta access" in my Polar sandbox organization.
    ```

    Uses the `benefits_create` operation of the [Polar MCP server](/integrate/mcp).
  </Tab>
</Tabs>

<CodeGroup>
```typescript TypeScript
const benefit = await polar.benefits.create({
  type: "feature_flag",
  description: "Beta access",
  properties: {},
  metadata: { tier: "pro" },
});
```

```python Python
benefit = polar.benefits.create(
    type="feature_flag",
    description="Beta access",
    properties={},
    metadata={"tier": "pro"},
)
```

```bash cURL
export BENEFIT_ID=$(curl -s -X POST https://sandbox-api.polar.sh/v1/benefits/ \
  -H "Authorization: Bearer $POLAR_ACCESS_TOKEN" \
  -H "Polar-Version: 2026-10" \
  -H "Content-Type: application/json" \
  -d '{
    "type": "feature_flag",
    "description": "Beta access",
    "properties": {},
    "metadata": { "tier": "pro" }
  }' | jq -r .id)
```
</CodeGroup>

Each type page lists its `properties`. Discord, GitHub and Slack benefits need a connection made in the dashboard first.

## Attach a benefit to a product

A product grants every benefit attached to it. Setting a product's benefits replaces the whole list, so send every benefit the product should keep.

<Tabs>
  <Tab title="Dashboard">
    - Open **Products** and select the product
    - Under **Automated Benefits**, select the benefit
    - Save the product
  </Tab>
  <Tab title="CLI">
    ```bash
    polar products update_benefits <product_id> --data '{ "benefits": ["<benefit_id>"] }'
    ```

    See [`polar products`](/integrate/cli/reference/products).
  </Tab>
  <Tab title="Prompt">
    ```text Prompt
    Attach the "Beta access" benefit to my Pro product in my Polar sandbox organization.
    ```

    Uses the `products_update_benefits` operation of the [Polar MCP server](/integrate/mcp).
  </Tab>
</Tabs>

<CodeGroup>
```typescript TypeScript
await polar.products.updateBenefits(product.id, {
  benefits: [benefit.id],
});
```

```python Python
polar.products.update_benefits(product.id, benefits=[benefit.id])
```

```bash cURL
curl -X POST https://sandbox-api.polar.sh/v1/products/$PRODUCT_ID/benefits \
  -H "Authorization: Bearer $POLAR_ACCESS_TOKEN" \
  -H "Polar-Version: 2026-10" \
  -H "Content-Type: application/json" \
  -d '{ "benefits": ["'"$BENEFIT_ID"'"] }'
```
</CodeGroup>

Existing customers of the product get the new benefit too. Removing a benefit from a product revokes it from the product's customers.

## Visibility

`visibility` decides whether customers see a benefit after purchase: in order confirmations, emails, the Customer Portal and the product's public benefit list.

| Dashboard | API value | Effect |
| --- | --- | --- |
| **Visible** | `public` | Shown to customers |
| **Hidden** | `private` | Granted, but never shown to customers |

Hidden benefits still appear in the customer's `granted_benefits` in the [customer state](/integrate/customer-state), so your application can read them.

You can only change visibility on **Custom**, **License Keys**, **Meter Credits** and **Feature Flag** benefits. Feature flags default to hidden, the others to visible. Discord, GitHub, file download and Slack benefits are always visible, because the customer has to act in the portal to receive them.

## Metadata

`metadata` is a key-value object on the benefit. It's returned as `benefit_metadata` on each entry of the customer state's `granted_benefits`, so your application can read configuration such as a plan tier or a limit without hardcoding benefit IDs. Feature flags rely on it. See [Feature flags](/features/benefits/feature-flags).

## Update or delete a benefit

Updating a benefit's properties updates existing grants: changing a Discord role, for example, moves every customer to the new role.

Deleting a benefit revokes it from every customer who holds it. Detach it from products instead if existing customers should keep it.

<Warning>
  Deleting a benefit can't be undone, and customers lose access right away.
</Warning>

In the dashboard:

- Open **Products → Benefits** and select the benefit
- Click **Edit Benefit** to change it
- Open the **…** menu and click **Delete Benefit** to delete it

The benefit's page also lists its **Benefit Grants**: who holds it and each grant's status.

| Task | CLI | MCP operation |
| --- | --- | --- |
| Update a benefit | `polar benefits update <id>` | `benefits_update` |
| Delete a benefit | `polar benefits delete <id>` | `benefits_delete` |
| List who holds a benefit | `polar benefits grants <id>` | `benefits_grants` |
| List grants across benefits | `polar benefit_grants list` | `benefit_grants_list` |

## Grant or revoke a benefit manually

<Note>Available from API version 2027-01.</Note>

You can grant a benefit to a customer without a purchase, revoke any grant, including one from a purchase, and undo a manual revocation. Meter Credits benefits can't be granted this way. Credit the meter directly instead, see [Credits](/features/usage-based-billing/credits).

- **Dashboard:** open **Customers** and select the customer. Under **Benefit Grants**, click **Grant benefit**. Each grant row has **Revoke**, and a manually revoked grant has **Unrevoke**.
- **Prompt:** "Grant the Beta access benefit to user_123 in my Polar sandbox organization." Uses the `benefit_grants_create` operation of the [Polar MCP server](/integrate/mcp). `benefit_grants_revoke` and `benefit_grants_update` revoke and restore grants. These have no CLI command yet.
- **API:** [`POST /v1/benefit-grants/`](/api-reference/next/benefit-grants/create-benefit-grant), [`DELETE /v1/benefit-grants/{id}`](/api-reference/next/benefit-grants/revoke-benefit-grant) and [`PATCH /v1/benefit-grants/{id}`](/api-reference/next/benefit-grants/update-benefit-grant).

Granting and revoking are asynchronous. The returned grant may not be granted yet. A manually revoked grant stays revoked through renewals until you undo the revocation.

## Grant errors

When Polar can't deliver a benefit, for example because the GitHub App lost access to the repository, the grant's `error` field holds the reason. Find failed grants under **Benefit Grants** on the benefit's page in **Products → Benefits**, or list them with `polar benefits grants <id>`.

## Webhooks

| Event | When |
| --- | --- |
| `benefit.created` | A benefit was created |
| `benefit.updated` | A benefit was updated |
| `benefit_grant.created` | A customer was granted a benefit |
| `benefit_grant.updated` | A grant changed, for example a license key was updated |
| `benefit_grant.cycled` | A subscription renewed and the grant was renewed with it |
| `benefit_grant.revoked` | A grant was revoked |

Each grant change also fires `customer.state_changed`, which is usually all you need. See [Webhook events](/integrate/webhooks/events).

<Visibility for="agents">
  Read access from the customer state (`GET /v1/customers/external/{external_id}/state`, `granted_benefits[].benefit_id` and `benefit_metadata`), not by listing grants. `visibility` only accepts `private` or `draft` on `custom`, `license_keys`, `meter_credit` and `feature_flag`; other types return a validation error. `POST /v1/products/{id}/benefits` replaces the full list. `DELETE /v1/benefits/{id}` revokes every grant. Manual grants (`benefit-grants` create, update, revoke) require API version `2027-01`.
</Visibility>
