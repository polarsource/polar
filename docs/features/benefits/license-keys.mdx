A **License Keys benefit** issues a unique license key to each customer who buys the product. Your software validates the key against Polar's API, so you don't host a license server. Polar also handles expiry, device activations, usage quotas and revocation when a subscription ends.

To check keys from your application, see [Validate license keys](/features/benefits/validate-license-keys).

## What the customer gets

A key such as `ACME-1C285B2D-6CE6-4BC7-B8BE-ADB6A7E304DA`, shown in the [Customer Portal](/features/customer-portal/introduction). Each customer gets their own key per benefit.

## Create it

<Tabs>
  <Tab title="Dashboard">
    - Open **Products** → **Benefits**
    - Click **Create Benefit**
    - Choose **License Keys** as the **Type**
    - Set the **Description** and an optional **Key prefix**
    - Turn on **Expires**, **Limit Activations** or **Limit Usage** if you need them
    - Click **Create**
  </Tab>
  <Tab title="CLI">
    ```bash
    polar benefits create --data '{
      "type": "license_keys",
      "description": "Desktop app license",
      "properties": {
        "prefix": "ACME",
        "activations": { "limit": 3, "enable_customer_admin": true }
      }
    }'
    ```

    See [`polar benefits`](/integrate/cli/reference/benefits).
  </Tab>
  <Tab title="Prompt">
    ```text Prompt
    Create a License Keys benefit called "Desktop app license" with the prefix ACME and up to 3 activations that customers can manage themselves, in my Polar sandbox organization.
    ```

    Uses the `benefits_create` operation of the [Polar MCP server](/integrate/mcp).
  </Tab>
</Tabs>

Then attach it to a product. See [Manage benefits](/features/benefits/introduction#attach-a-benefit-to-a-product).

## Options

| Dashboard | API property | Default |
| --- | --- | --- |
| **Key prefix** | `properties.prefix` | None |
| **Expires**, after N days, months or years | `properties.expires.ttl` (> 0) and `properties.expires.timeframe` (`day`, `month`, `year`) | No expiry |
| **Limit Activations** | `properties.activations.limit` (> 0) | No activations |
| **Enable user to deactivate instances via Polar** | `properties.activations.enable_customer_admin` | Off |
| **Limit Usage** | `properties.limit_usage` (> 0) | Unlimited |
| **Visibility** | `visibility` | **Visible** (`public`) |

Changes to these options apply to keys already issued, not just new ones.

### Expiration

How long a key stays valid depends on how the customer got it:

- **One-time purchases:** with **Expires** on, the key expires `ttl` days, months or years after the purchase.
- **Subscriptions:** the expiration setting is ignored. Keys granted through a subscription have no `expires_at`, stay valid while the subscription is active, and are revoked when it ends.

So the same benefit can produce keys with an expiry date (one-time products) and keys without one (subscription products).

<Note>
  For subscription products, check the key's `status` when validating rather than `expires_at`. A revoked key fails validation.
</Note>

<Warning>
  Polar manages `expires_at`. Whenever the benefit or the customer's grant is updated, Polar re-applies the benefit's expiration to the key, or removes it for subscription keys. A manual change to `expires_at` through the API is overwritten.
</Warning>

### Activations

With **Limit Activations**, your application must activate a key on each device or instance before validating it there. Polar refuses activations beyond the limit. Each activation has a `label` and can store `conditions` (for example a major version or machine ID) that later validations must match.

With **Enable user to deactivate instances via Polar**, customers can remove activations from the Customer Portal, for example when they replace a laptop. Otherwise, your application deactivates them through the API.

### Usage limit

**Limit Usage** gives each key a quota. Your application consumes it by passing `increment_usage` when validating. Validation fails once the request would exceed the remaining quota. Use it for credits, API calls or generations tied to a key.

## Key statuses

| Dashboard | API `status` | Meaning | Validates |
| --- | --- | --- | --- |
| **Granted** | `granted` | Active | Yes, unless expired |
| **Disabled** | `disabled` | Turned off by you. Set it back to **Granted** to re-enable | No |
| **Revoked** | `revoked` | The benefit was revoked, for example when a subscription ended | No |

## Manage keys

In the dashboard, open the benefit under **Products** → **Benefits** and use the **License Keys** tab. Select a key to see its usage, validations and activations, change its status, or rotate it.

| Task | CLI | MCP operation |
| --- | --- | --- |
| List keys, filtered by benefit or status | `polar license_keys list --benefit-id <id>` | `license_keys_list` |
| Get a key and its activations | `polar license_keys get <id>` | `license_keys_get` |
| Disable a key, or change its usage or limits | `polar license_keys update <id> --status disabled` | `license_keys_update` |
| Rotate a key | `polar license_keys rotate <id>` | `license_keys_rotate` |
| Get an activation | `polar license_keys get_activation <id> <activation_id>` | `license_keys_get_activation` |

See [`polar license_keys`](/integrate/cli/reference/license_keys). Changes to a key fire the `benefit_grant.updated` webhook.

### Rotate a key

If a key is exposed, rotate it. Rotation generates a new key string on the same license key record. The old string stops validating immediately. Status, usage, limits, expiry and activations are kept.

You can rotate from the dashboard, the CLI, or [`POST /v1/license-keys/{id}/rotate`](/api-reference/current/license_keys/rotate-license-key). Customers can rotate their own key from the Customer Portal. Only `granted` and `disabled` keys can be rotated. Rotating a revoked key returns a `400` error.

## Customer experience

After paying, the customer finds the key in the Customer Portal. They can:

- View and copy the key
- See its expiry date and remaining usage, when set
- Deactivate activations, when you allow it
- Rotate the key if it's exposed

## Revocation

When the benefit is revoked, for example when a subscription ends, the key's status becomes `revoked` and it stops validating. The customer no longer sees it in the portal.

## Visibility

Configurable, visible by default. A hidden License Keys benefit still issues a key, but the customer never sees it. Hide it only if you deliver the key some other way.
