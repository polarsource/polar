A **metered price** charges a customer for the usage a [meter](/features/usage-based-billing/meters) records, billed after the period ends. Read [Usage: events & meters](/concepts/usage) for how events become usage. This page covers adding a metered price to a product and how usage is invoiced.

Set up your events and meter first, then add the metered price to a recurring product. Metered prices aren't supported on one-time products.

The code examples use API version `2026-10` and the sandbox.

## Metered pricing

Under **Pricing model**, a metered price is one of three models:

| Dashboard | API | The customer pays |
| --- | --- | --- |
| **Flat price per unit** | `metered_unit` with `unit_amount` | The same rate for every unit |
| **Volume** | `metered_tiers` with `type: "volume"` | The rate of the tier the total falls in, on every unit |
| **Graduated** | `metered_tiers` with `type: "graduated"` | Each tier's range at its own rate, summed |

Rates are in cents per single unit. `unit_amount` accepts up to 12 decimal places, so `"0.002"` is \$0.00002 per unit. How the price is displayed to customers, such as `$20 / 1M tokens`, comes from the meter's [unit](/features/usage-based-billing/meters#unit) setting.

### Defining tiers

Volume and graduated take the same tiers. A tier has an upper bound and a rate. The bound is inclusive, and each tier starts where the previous one ended. The last tier is always unbounded, since usage has no ceiling.

With tiers of up to 1,000 units at \$0.10 and beyond at \$0.08, 1,400 units cost:

- Volume: 1,400 × \$0.08 = \$112. Every unit gets the lower rate.
- Graduated: 1,000 × \$0.10 + 400 × \$0.08 = \$132. Each range keeps its own rate.

### Cap

A **Cap amount** (`cap_amount`, in cents) limits what the customer pays for the meter in a period, whatever their usage.

## Add a metered price to a product

<Tabs>
  <Tab title="Dashboard">
    - Open **Products** and select a recurring product, or click **New Product**
    - Under **Pricing**, add a **Metered price**
    - Select the meter
    - Under **Pricing model**, choose **Flat price per unit**, **Volume** or **Graduated**
    - Enter the **Amount per unit**, or the tiers
    - Optionally, set a **Cap amount**
  </Tab>
  <Tab title="CLI">
    ```bash
    polar products create --name "Pro" --recurring-interval month \
      --prices '[
        { "amount_type": "fixed", "price_amount": 2000 },
        { "amount_type": "metered_unit", "meter_id": "<meter_id>", "unit_amount": "0.002", "cap_amount": 10000 }
      ]'
    ```
  </Tab>
  <Tab title="Prompt">
    ```text Prompt
    Create a monthly product called Pro in my Polar sandbox with a $20 base price and a metered price of $0.00002 per unit on my AI tokens meter, capped at $100.
    ```

    Uses the `products_create` operation of the [Polar MCP server](/integrate/mcp).
  </Tab>
</Tabs>

For tiered usage, use `amount_type: "metered_tiers"` with `tiers: { type: "graduated", tiers: [{ bound: 1000, unit_amount: "10" }, { bound: null, unit_amount: "8" }] }`.

A product can have several metered prices, one per meter, to bill on more than one dimension. To give customers included usage before overage, add a [Meter Credits benefit](/features/usage-based-billing/credits).

<Visibility for="agents">
  Metered prices are `metered_unit` (with `unit_amount`, a decimal string in cents) or `metered_tiers` (with `tiers`), each with `meter_id` and optional `cap_amount` in cents. They're only valid on recurring products. Each meter can appear once per currency.
</Visibility>

## When usage is invoiced

By default, usage follows the subscription's billing period. On a monthly subscription, usage is added up over the month and invoiced at renewal with the rest of the subscription. On a yearly subscription, it's invoiced at the yearly renewal.

To invoice usage more often than the subscription renews, for example monthly on a yearly plan, set a [meter cycle](#meter-cycle).

When a subscription is canceled at period end, usage keeps being tracked until the period ends. The final usage is invoiced then, even though the subscription doesn't renew.

## Meter cycle

A meter cycle lets metered usage run on its own cadence, independent of the billing interval. It's set on the product with `meter_interval` and `meter_interval_count`, or with the **Separate meter cycle** toggle in the product's pricing section.

The common case is a yearly plan with monthly usage: the customer pays the base price once a year, while overage is invoiced and [credits](/features/usage-based-billing/credits) are granted every month.

At the end of each meter period, Polar:

1. Invoices the period's usage as a separate order.
2. Resets the customer's meters.
3. Grants the [Meter Credits benefit](/features/usage-based-billing/credits) again, applying rollover if it's enabled.

Meters are reset and credits granted even when there's no usage to invoice. If the period's usage is below the minimum chargeable amount, no payment is taken: the amount is added to the customer's balance and applied to their next order.

Without a meter cycle, all of this happens once per billing period, at renewal.

### Alignment with the billing interval

The meter cycle must divide the billing interval evenly, so both cycles line up again at every renewal. The meter cycle starts on the same anchor day as the subscription.

| Billing interval  | Allowed meter cycles                                              |
| ----------------- | ----------------------------------------------------------------- |
| Every _n_ days    | Every _m_ days, where _m_ divides _n_                             |
| Every _n_ weeks   | Every _m_ weeks, where _m_ divides _n_, or every _m_ days, where _m_ divides _7n_ |
| Every _n_ months  | Every day, or every _m_ months, where _m_ divides _n_             |
| Every _n_ years   | Every day, or every _m_ months, where _m_ divides _12n_, or every _m_ years, where _m_ divides _n_ |

For example, a yearly plan accepts a meter cycle of 1, 2, 3, 4, 6 or 12 months, but not 5 months or 1 week. Weeks don't fit evenly into months, so weekly meter cycles aren't available on monthly or yearly plans.

<Warning>
  The meter cycle can't be changed once it's set on a product. Existing
  subscriptions keep the meter cycle they were created with.
</Warning>

### At renewal and other boundaries

- **Renewal**: the last meter period of a billing period is invoiced in the regular renewal order, together with the base price. No separate `subscription_meter_cycle` order is created, and the meter cycle restarts from the new billing period.
- **Trials**: the meter cycle starts when the trial converts to a paid subscription.
- **Plan change**: usage accrued so far is invoiced right away on the previous product's prices, before the switch takes effect.
- **Immediate cancellation**: usage up to the cancellation is invoiced right away. A cancellation at the end of the period invoices the final usage at the end of that period, as usual.

### Discounts

A [discount](/features/discounts) on the subscription applies to the whole renewal order, usage included. On meter cycle orders, a percentage discount applies and a fixed-amount discount doesn't.

### Failed payments

A failed meter cycle order is retried on the same schedule as [failed subscription payments](/features/subscriptions/failed-payments): after 2, 7, 14 and 21 days. It never affects the subscription itself: the subscription stays `active`, keeps its benefits, and isn't revoked. If every retry fails, the order is voided.

If the subscription itself becomes `past_due` because its renewal payment failed, the meter cycle is paused: no usage is invoiced, meters aren't reset and no credits are granted. Usage keeps being recorded. When the subscription recovers, the accrued usage is invoiced in one order, meters are reset and credits are granted again.

### Customer emails

Each meter cycle order sends the customer a **Your {product} usage invoice** email with a link to the customer portal. It's controlled by the same setting as subscription renewal emails, so disabling renewal emails disables these too.

### Webhooks

Each meter cycle order emits `order.created` and `order.paid` like any other order. Check `billing_reason` to tell them apart from renewals. Meter cycles don't emit `subscription.cycled`, which only fires at renewal.

## Customer Portal

Customers see their estimated charges for each meter in the [Customer Portal](/features/customer-portal/introduction) while **Settings → Customer Portal → Show metered usage** is on.
