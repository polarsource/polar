title: "Credits"
description: "Include prepaid usage in a product with the Meter Credits benefit, grant or reverse credits by hand, and track each customer's balance."
---

**Credits** are prepaid units on a meter. Usage draws the balance down before anything is billed, so a customer can buy 1M tokens up front instead of getting a bill at the end of the month. See [Usage](/concepts/usage) for how credits and metered prices fit together.

There are two ways to credit a customer:

- The **Meter Credits** benefit, attached to a product. Credits are granted on purchase, and on every cycle for subscriptions.
- **Manual credits**, granted to one customer from the dashboard or API, for example as a goodwill gesture.

## How the balance works

A customer's **balance** on a meter is credited units minus consumed units. Usage draws from it first. What happens when it runs out depends on the product:

- **With a metered price** on the same meter, usage beyond the credits is billed as overage on the next invoice.
- **Without one**, usage is never charged. The balance goes negative and you decide what to do.

<Warning>
  Polar doesn't block usage when a balance runs out. Events are always accepted. Check the balance in your application and stop serving requests when you need to. See [Track the balance](#track-the-balance).
</Warning>

## The Meter Credits benefit

Attach a **Meter Credits** benefit to a product to include credits in it.

| Field | API property | Description |
| --- | --- | --- |
| **Meter** | `meter_id` | The meter to credit |
| **Number of credited units** | `units` | A whole number greater than 0 |
| **Rollover unused credits** | `rollover` | Carry unused units into the next period. Off by default. |

<Tabs>
  <Tab title="Dashboard">
    - Open **Products → Benefits**
    - Click **Create Benefit**
    - Set the type to **Meter Credits**
    - Enter a **Description**, such as "1M tokens per month"
    - Pick the **Meter** and set **Number of credited units**
    - Check **Rollover unused credits** if unused units should carry over
    - Save, then add the benefit to a product
  </Tab>
  <Tab title="CLI">
    ```bash
    polar benefits create --type meter_credit --description "1M tokens per month" \
      --properties '{"meter_id": "<meter-id>", "units": 1000000, "rollover": false}'
    ```

    Then attach it with `polar products update_benefits`. See the [`benefits` reference](/integrate/cli/reference/benefits).
  </Tab>
  <Tab title="Prompt">


    Uses the `benefits_create` and `products_update_benefits` operations of the [Polar MCP server](/integrate/mcp).
  </Tab>
</Tabs>

### When credits are granted

- **One-time products:** once, at purchase.
- **Subscriptions:** at the start of every billing cycle, whatever its interval: daily, weekly, monthly or yearly.
- **Subscriptions with a [meter cycle](/features/usage-based-billing/billing#meter-cycle):** at the start of every meter period instead. A yearly plan with a monthly meter cycle grants credits every month.

No credits are granted while a subscription is `past_due`. When the benefit is revoked, for example because the subscription ended, its credits are removed.

### Rollover

With **Rollover unused credits** on, units left at the end of a period are added to the next one. Without it, they expire. Changing the setting only affects credits granted after the change.

## Grant credits manually

Manual credits are added on top of any credits from a benefit. Use them for goodwill, a top-up outside a purchase, or a correction.

<Note>
  Granting and reversing manual credits through the API is available from API version 2027-01. The dashboard works on every version.
</Note>

<Tabs>
  <Tab title="Dashboard">
    - Open **Customers** and select the customer
    - Choose **Add Credits** from the customer menu, or click **Add credits** on a meter row in the **Usage** tab
    - Pick the **Meter** and enter the **Credits**
    - Leave **Rollover unused credits to the next billing cycle** checked, or uncheck it
    - Click **Add credits**

    The panel previews the new balance and, for billed meters, how much of the current overage the credits cover. Rollover is on by default here, unlike in the API.
  </Tab>
  <Tab title="CLI">
    ```bash
    polar customer_meters credits --customer-id <customer-id> --meter-id <meter-id> \
      --units 100 --external-id goodwill-2026-11-25
    ```

    See the [`customer_meters` reference](/integrate/cli/reference/customer_meters).
  </Tab>
  <Tab title="Prompt">
    ```text Prompt
    Give customer user_123 100 extra credits on the AI tokens meter in my Polar sandbox organization, as a goodwill gesture.
    ```

    Uses the `customer_meters_credits` operation of the [Polar MCP server](/integrate/mcp).
  </Tab>
</Tabs>

From your code, with the `2027-01` SDK:

<CodeGroup>
```typescript TypeScript
import { createPolar } from "@polar-sh/sdk/2027-01";

const polar = createPolar({
  accessToken: process.env.POLAR_ACCESS_TOKEN!,
  environment: "sandbox",
});

const credit = await polar.customerMeters.credits({
  customer_id: customer.id,
  meter_id: meter.id,
  units: 100,
  rollover: false,
  external_id: "goodwill-2026-11-25",
});
```

```python Python
import os

from polar.v2027_01 import Polar

polar = Polar(os.environ["POLAR_ACCESS_TOKEN"], environment="sandbox")

credit = polar.customer_meters.credits(
    customer_id=customer.id,
    meter_id=meter.id,
    units=100,
    rollover=False,
    external_id="goodwill-2026-11-25",
)
```

```bash cURL
export CREDIT_ID=$(curl -s -X POST https://sandbox-api.polar.sh/v1/customer-meters/credits \
  -H "Authorization: Bearer $POLAR_ACCESS_TOKEN" \
  -H "Polar-Version: 2027-01" \
  -H "Content-Type: application/json" \
  -d '{
    "customer_id": "'"$CUSTOMER_ID"'",
    "meter_id": "'"$METER_ID"'",
    "units": 100,
    "rollover": false,
    "external_id": "goodwill-2026-11-25"
  }' | jq -r .id)
```
</CodeGroup>

- `units` is a whole number from 1 to 1,000,000,000.
- `rollover` defaults to `false` in the API: unused credits expire at the end of the meter period.
- `external_id` is optional. Retrying with the same `external_id` and the same request returns the original credit instead of granting it twice. Reusing it for a different credit returns a `409`.
- The meter must belong to the customer's organization and can't be archived.
- The access token needs the `customers:write` scope.

The response is the `meter.credited` event that was recorded. The balance is updated before the response returns. If the meter is being updated at the same moment, it catches up shortly after.

A Meter Credits benefit can't be granted by hand through the benefit grants API. Use this endpoint instead.

### Reverse a manual credit

Reverse a credit added by mistake with **Reverse** on the credit in the customer meter's history, or from the API with the ID of the `meter.credited` event:

<CodeGroup>
```typescript TypeScript
await polar.customerMeters.reverseCredit(credit.id);
```

```python Python
polar.customer_meters.reverse_credit(credit.id)
```

```bash cURL
curl -X POST "https://sandbox-api.polar.sh/v1/customer-meters/credits/$CREDIT_ID/reverse" \
  -H "Authorization: Bearer $POLAR_ACCESS_TOKEN" \
  -H "Polar-Version: 2027-01"
```
</CodeGroup>

Your agent can do it with the `customer_meters_reverse_credit` MCP operation. There's no CLI command for it.

A reversal removes only the units the customer hasn't used. Units already consumed stay consumed. Usage draws from non-rollover credits before rollover credits. A reversal is rejected when:

- The credit is older than 7 days.
- The credit was granted in a period that has already been invoiced.
- The credit has already been reversed. Each credit can be reversed once.
- All of its units have been used.

Only manual credits can be reversed. To remove credits from a Meter Credits benefit, revoke the benefit.

## Credit history

Every credit, reversal and revocation is recorded as a `meter.credited` system event on the customer. Its metadata contains:

| Key | Description |
| --- | --- |
| `meter_id` | The credited meter |
| `units` | The number of units. Negative for revocations and reversals. |
| `rollover` | Whether unused units carry over to the next meter period |
| `reason` | `benefit` for the Meter Credits benefit, including rolled-over units, or `manual` for the dashboard or API |

A reversal has `parent_id` set to the ID of the credit it reverses. The history is on the customer's meter page in the dashboard.

## Track the balance

To check one customer by hand, open **Customers**, select the customer and open the **Usage** tab. Each meter shows **Consumed**, **Credited**, **Balance** and **Overages**.

In your application, read the balance before you serve usage that needs credits:

- The [customer state](/integrate/customer-state) lists every active meter with `consumed_units`, `credited_units` and `balance`.
- The [Customer Meters API](/api-reference/current/customer_meters/list-customer-meters) returns the same per meter. From the CLI: `polar customer_meters list --external-customer-id user_123`.
- `polar.metering()` reads one meter for one customer: `await metering.meter(meterId, { external_customer_id: "user_123" })`. See [Send events](/features/usage-based-billing/event-ingestion#bind-events-to-a-customer).

The `customer.state_changed` webhook fires when the state changes, so you can cache it instead of polling.
