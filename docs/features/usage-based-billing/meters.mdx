A **meter** turns events into a usage number per customer. Its **filter** selects events, and its **aggregation** adds them up: count them, or sum, average, or take the minimum or maximum of a property. A meter works on its own as a usage report. Metered prices and credits attach to a meter when you want to charge for that usage. See [Usage](/concepts/usage) for the full picture.

The examples on this page use the sandbox and API version `2026-10`.

## Create a meter

This meter sums `total_tokens` across `ai_usage` events, the events sent in [Send events](/features/usage-based-billing/event-ingestion).

<Tabs>
  <Tab title="Dashboard">
    - Open **Products → Meters**
    - Click **Create Meter**
    - Set **Name** to "AI tokens"
    - Under **Filters**, add a condition: **Name** equals `ai_usage`
    - Set **Aggregation** to **Sum** over the property `total_tokens`
    - Set **Unit** to **Token**
    - Click **Create Meter**
  </Tab>
  <Tab title="CLI">
    ```bash
    polar meters create --name "AI tokens" --unit token \
      --filter '{"conjunction":"and","clauses":[{"property":"name","operator":"eq","value":"ai_usage"}]}' \
      --aggregation '{"func":"sum","property":"total_tokens"}'
    ```

    See the [`meters` reference](/integrate/cli/reference/meters).
  </Tab>
  <Tab title="Prompt">
    ```text Prompt
    Create a meter called "AI tokens" in my Polar sandbox organization that sums total_tokens across ai_usage events, with the token unit.
    ```

    Uses the `meters_create` operation of the [Polar MCP server](/integrate/mcp).
  </Tab>
</Tabs>

From your code:

<CodeGroup>
```typescript TypeScript
const meter = await polar.meters.create({
  name: "AI tokens",
  unit: "token",
  filter: {
    conjunction: "and",
    clauses: [{ property: "name", operator: "eq", value: "ai_usage" }],
  },
  aggregation: { func: "sum", property: "total_tokens" },
});
```

```python Python
meter = polar.meters.create(
    name="AI tokens",
    unit="token",
    filter={
        "conjunction": "and",
        "clauses": [{"property": "name", "operator": "eq", "value": "ai_usage"}],
    },
    aggregation={"func": "sum", "property": "total_tokens"},
)
```

```bash cURL
export METER_ID=$(curl -s -X POST https://sandbox-api.polar.sh/v1/meters/ \
  -H "Authorization: Bearer $POLAR_ACCESS_TOKEN" \
  -H "Polar-Version: 2026-10" \
  -H "Content-Type: application/json" \
  -d '{
    "name": "AI tokens",
    "unit": "token",
    "filter": {
      "conjunction": "and",
      "clauses": [{ "property": "name", "operator": "eq", "value": "ai_usage" }]
    },
    "aggregation": { "func": "sum", "property": "total_tokens" }
  }' | jq -r .id)
```
</CodeGroup>

The name needs at least 3 characters. It's shown to customers on invoices and in the Customer Portal.

A new meter counts events you've already sent, so you can add a meter later without changing your code.

## Filters

A filter is a `conjunction` (`and` or `or`) and a list of `clauses`. Each clause compares one property of the event with a value. A clause can itself be a filter, so you can nest groups. In the dashboard, the top level holds condition groups: **Add condition group** adds one and **Add condition** adds a clause to it.

```json
{
  "conjunction": "or",
  "clauses": [
    { "property": "name", "operator": "eq", "value": "ai_usage" },
    {
      "conjunction": "and",
      "clauses": [
        { "property": "name", "operator": "eq", "value": "agent_run" },
        { "property": "model", "operator": "like", "value": "gpt" }
      ]
    }
  ]
}
```

### Properties

| Property | Matches |
| --- | --- |
| `name` | The event name |
| `source` | `user` for your events, `system` for events Polar writes |
| `timestamp` | The event time, compared as a Unix timestamp in seconds |
| Any other key | The metadata key with that name. `model` reads `metadata.model`. |

Use dot notation to reach into `_llm` and `_cost`, for example `_llm.total_tokens` or `_cost.amount`. A path has at most 5 levels and 255 characters. A leading `metadata.` is optional.

### Operators

| Dashboard | API | Works on |
| --- | --- | --- |
| equals | `eq` | Strings, numbers, booleans |
| does not equal | `ne` | Strings, numbers, booleans |
| is greater than | `gt` | Numbers, strings |
| is greater than or equal to | `gte` | Numbers, strings |
| is less than | `lt` | Numbers, strings |
| is less than or equal to | `lte` | Numbers, strings |
| contains | `like` | Strings |
| does not contain | `not_like` | Strings |

A value is a string (up to 1,000 characters), an integer or a boolean. Types must match: the string `"77"` doesn't equal the number `77`. The dashboard reads what you type as a number first, then as `true` or `false`, and otherwise as a string.

## Aggregation

| Function | API | Result |
| --- | --- | --- |
| **Count** | `count` | The number of matching events. Takes no property. |
| **Sum** | `sum` | The sum of a property |
| **Average** | `avg` | The average of a property |
| **Minimum** | `min` | The smallest value of a property |
| **Maximum** | `max` | The largest value of a property |
| **Unique** | `unique` | The number of distinct values of a property. Deprecated. |

<Note>
  **Unique** is deprecated, and some organizations can't create it. Use one of the other functions for new meters.
</Note>

Like filters, the aggregation property is a metadata key or a dot path such as `_llm.total_tokens`.

```json
[
  { "name": "ai_usage", "external_customer_id": "user_123", "metadata": { "total_tokens": 10 } },

  { "name": "ai_usage", "external_customer_id": "user_123", "metadata": { "total_tokens": 30 } },
  { "name": "ai_usage", "external_customer_id": "user_123", "metadata": { "total_tokens": 30 } }

```

- **Count**: 4
- **Sum**: 90
- **Average**: 22.5
- **Minimum**: 10
- **Maximum**: 30
- **Unique**: 3

## Unit

The unit controls how prices on this meter are **displayed** to customers: on invoices, in the Customer Portal and at checkout. It doesn't change how usage is counted or billed.

| Unit | API | Display | Use for |
| --- | --- | --- | --- |
| **Scalar** | `scalar` | $0.05 / unit | Generic counts: API calls, requests, events. The default. |
| **Token** | `token` | $20.00 / 1M tokens | LLM tokens |
| **Custom** | `custom` | Your own label | Anything else |

With **Custom**, two more fields appear:

- **Unit label** (`custom_label`): the name shown after the price, up to 32 characters. `gigabyte` shows as `$0.023 / gigabyte`. Required.
- **Unit Multiplier** (`custom_multiplier`): shows the price per that many units. `1000` shows the price per 1,000 units. Defaults to 1.

The multiplier only changes the display. The price you set is still per single unit.

## Read usage

The meter's page in **Products → Meters** has three tabs:

- **Overview**: a usage chart and the **Current Month**, **Previous Month** and **All Time** totals.
- **Events**: the events the meter matched.
- **Customers**: usage per customer.

To read usage over a time range from your code, call the quantities endpoint. Pass `external_customer_id` or `customer_id` to scope it to one customer:

<CodeGroup>
```typescript TypeScript
const quantities = await polar.meters.quantities(meter.id, {
  start_timestamp: "2026-11-01T00:00:00Z",
  end_timestamp: "2026-12-01T00:00:00Z",
  interval: "day",
  external_customer_id: "user_123",
});
```

```python Python
quantities = polar.meters.quantities(
    meter.id,
    start_timestamp="2026-11-01T00:00:00Z",
    end_timestamp="2026-12-01T00:00:00Z",
    interval="day",
    external_customer_id="user_123",
)
```

```bash cURL
curl -G "https://sandbox-api.polar.sh/v1/meters/$METER_ID/quantities" \
  -H "Authorization: Bearer $POLAR_ACCESS_TOKEN" \
  -H "Polar-Version: 2026-10" \
  --data-urlencode "start_timestamp=2026-11-01T00:00:00Z" \
  --data-urlencode "end_timestamp=2026-12-01T00:00:00Z" \
  --data-urlencode "interval=day" \
  --data-urlencode "external_customer_id=user_123"
```
</CodeGroup>

```bash
polar meters quantities $METER_ID --external-customer-id user_123 \
  --start-timestamp 2026-11-01T00:00:00Z --end-timestamp 2026-12-01T00:00:00Z --interval day
```

For a customer's current balance against their credits, read the [customer state](/integrate/customer-state) or `polar customer_meters list --external-customer-id user_123`.

## Edit a meter

Open the meter and click **Edit Meter**, or call `polar meters update <id>`. You can always change the name and unit.

**The filter and aggregation lock** once the meter has billed events. Changing them then would change usage customers were already charged for. The API rejects the change with "This field can't be updated because the meter is already aggregating events." Create a new meter instead.

## Archive a meter

Archive a meter you no longer use with **Archive Meter** on its page, or `polar meters update <id> --is-archived`. Polar blocks archiving while the meter is still used by:

- A metered price on an active product.
- An active subscription that bills it.
- A **Meter Credits** benefit.

Archived meters stop counting toward billing. **Unarchive Meter** restores it.

<Visibility for="agents">
  Create meters in the sandbox until the user says otherwise. Over HTTP this is `POST /v1/meters/` with `name`, `filter` and `aggregation`. Filter operators are `eq`, `ne`, `gt`, `gte`, `lt`, `lte`, `like`, `not_like`. Aggregation functions are `count`, `sum`, `avg`, `min`, `max`; don't use the deprecated `unique`. Don't try to change `filter` or `aggregation` on a meter that has billed events; create a new meter.
</Visibility>
