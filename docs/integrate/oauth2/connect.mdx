Connecting a user takes three requests: send them to Polar to approve access, exchange the code Polar returns for tokens, and call the API with the access token. You need an [OAuth 2.0 client](/integrate/oauth2/setup) first.

The examples use the sandbox. In production, use `https://polar.sh` for the authorization URL and `https://api.polar.sh` for the API.

## Authorize

Redirect the user to the authorization URL:

```text
https://sandbox.polar.sh/oauth2/authorize?
  response_type=code
  &client_id=CLIENT_ID
  &redirect_uri=https%3A%2F%2Fexample.com%2Fcallback
  &scope=openid%20email
```

The parameters follow the [OpenID Connect specification](https://openid.net/specs/openid-connect-core-1_0.html#AuthRequest). The main ones:

<ParamField path="response_type=code" type="string" required>
  The authorization code flow, the only flow Polar supports.
</ParamField>

<ParamField path="client_id" type="string" required>
  The Client ID of your OAuth 2.0 client.
</ParamField>

<ParamField path="redirect_uri" type="string" required>
  Where Polar sends the user after they approve access. It must be one of the client's **Redirect URIs**.
</ParamField>

<ParamField path="scope" type="string" required>
  Space-separated scopes to request. Each must be one of the client's **Scopes**.
</ParamField>

<ParamField path="sub_type=organization" type="string">
  Optional. Makes the user pick exactly one organization on the consent screen, so the token is limited to it.
</ParamField>

The user sees a consent screen listing the scopes you asked for. When they approve, Polar redirects them to your `redirect_uri` with a one-time `code` in the query string.

Polar issues **user-scoped** access tokens, tied to the user who approved access. On the consent screen, the user can limit the token to specific organizations. By default it can access all of their organizations, including ones they join later. Access always follows the user's current membership: if they leave an organization, the token loses access to it. To see which organizations a token is limited to, [introspect it](/api-reference/current/oauth2/introspect-token). The `organizations` array in the response is empty when the token isn't limited.

## Exchange the code for tokens

Send the code to the token endpoint, authenticated with your Client ID and Client Secret:

```bash cURL
curl -X POST https://sandbox-api.polar.sh/v1/oauth2/token \
  -H "Content-Type: application/x-www-form-urlencoded" \
  -d grant_type=authorization_code \
  -d code=AUTHORIZATION_CODE \
  -d client_id=CLIENT_ID \
  -d client_secret=CLIENT_SECRET \
  -d redirect_uri=https://example.com/callback
```

The response:

```json
{
  "token_type": "Bearer",
  "access_token": "polar_at_u_XXX",
  "expires_in": 864000,
  "refresh_token": "polar_rt_u_XXX",
  "scope": "openid email",
  "id_token": "ID_TOKEN"
}
```

- `access_token` authenticates API requests on behalf of the user, until `expires_in` seconds have passed.
- `refresh_token` gets a new access token when the current one expires.
- `id_token` is a signed JWT with the user's identity, as defined by [OpenID Connect](https://openid.net/specs/openid-connect-core-1_0.html#IDToken).

The token endpoint is a standard OAuth 2.0 endpoint and doesn't need a `Polar-Version` header. See [Request Token](/api-reference/current/oauth2/request-token).

### Refresh the access token

```bash cURL
curl -X POST https://sandbox-api.polar.sh/v1/oauth2/token \
  -H "Content-Type: application/x-www-form-urlencoded" \
  -d grant_type=refresh_token \
  -d refresh_token=polar_rt_u_XXX \
  -d client_id=CLIENT_ID \
  -d client_secret=CLIENT_SECRET
```

Each refresh returns a new refresh token as well. Store it and use it next time.

### Public clients

A **public client** can't keep a secret, because its code runs on the user's device: single-page apps, mobile and desktop apps. If, and only if, the client's **Client Type** is **Public Client**, the token endpoint doesn't need `client_secret`. Instead, the flow must use [PKCE](https://oauth.net/2/pkce/): send a `code_challenge` when you authorize, and the matching `code_verifier` when you exchange the code.

## Make authenticated requests

Send the access token as a bearer token, like any other Polar token:

<CodeGroup>
```typescript TypeScript
import { createPolar } from "@polar-sh/sdk/2026-10";

const polar = createPolar({
  accessToken: userAccessToken,
  environment: "sandbox",
});

const organizations = await polar.organizations.list();
```

```python Python
from polar.v2026_10 import Polar

polar = Polar(user_access_token, environment="sandbox")

organizations = polar.organizations.list()
```

```bash cURL
curl https://sandbox-api.polar.sh/v1/organizations/ \
  -H "Authorization: Bearer polar_at_u_XXX" \
  -H "Polar-Version: 2026-10"
```
</CodeGroup>

The token can only do what its scopes allow, in the organizations it can access. When it can access several organizations, pass `organization_id` on requests that create resources.

To disconnect a user, [revoke the token](/api-reference/current/oauth2/revoke-token).

<Visibility for="agents">
  Never ship a Client Secret in browser or mobile code: use a Public Client with PKCE there. Store refresh tokens server-side and replace them after every refresh. Use the sandbox (`sandbox.polar.sh`, `sandbox-api.polar.sh`) until the user says otherwise.
</Visibility>
