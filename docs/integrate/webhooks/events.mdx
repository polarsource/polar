Polar sends one webhook event per change in your organization. Each payload has a `type`, such as `order.paid`, a `timestamp` and the changed object in `data`, shaped by the endpoint's [API version](/integrate/webhooks/endpoints#api-version). Select a card for the full payload schema.

**Not sure which to pick?** For granting and revoking access, `customer.state_changed` alone is usually enough: it carries the customer's active subscriptions, granted benefits and meter balances. See [Customer state](/integrate/customer-state). For fulfilling one-time purchases, use `order.paid`.

<Visibility for="agents">
  Prefer `customer.state_changed` for access control and `order.paid` for fulfillment. `subscription.canceled` doesn't end access: the customer keeps it until `subscription.revoked`. Don't rely on delivery order across events; read `status` and timestamps from the payload.
</Visibility>

#### Cancellation sequences

When a subscription is canceled, the events triggered depend on whether the cancellation is immediate or scheduled for the end of the billing period.

**End-of-period cancellation (default)**

When a subscription is **canceled** (by customer action from the portal or by you from the dashboard or API), the following events are sent immediately:

1. `subscription.updated`
2. `subscription.canceled`

Both events contain the same subscription data. The subscription is still `active`, with `cancel_at_period_end` set to `true`.

At the end of the billing period, the subscription is revoked: billing stops and benefits are revoked. These events follow:

3. `subscription.updated`
4. `subscription.revoked`

Both events contain the same subscription data. The subscription is now `canceled`.

**Immediate revocation**

When you cancel a subscription with **immediate revocation**, these events are sent at once:

1. `subscription.updated`
2. `subscription.canceled`
3. `subscription.revoked`

All three events contain the same subscription data. The subscription is `canceled` immediately.

#### Renewal sequences

When a subscription renews, events arrive in two steps: the new period starts, then the payment is processed.

**Initial renewal events**

When a subscription reaches its renewal date, these events are sent immediately, if the endpoint subscribes to them:

1. `subscription.cycled`
2. `subscription.updated`
3. `order.created`

`subscription.cycled` fires only on a new billing period, so you can act on a renewal without inspecting `billing_reason` on the order. It also fires when a trial converts to a paid subscription, since that starts a period too: read `status` to tell the two apart.

The subscription shows the new period in `current_period_start` and `current_period_end`.

The order is the invoice for the new period. With usage-based billing, its total includes usage from the past period. Its status is `pending` at this stage.

**Payment processing events**

Shortly after, Polar charges the customer for the new order. Once the payment is successfully processed, the following events are sent:

4. `order.updated`
5. `order.paid`

Both events contain the same order, now with status `paid`.

#### Pause sequences

Pausing is scheduled for the end of the current billing period, much like an end-of-period cancellation.

When a subscription is **paused** (by customer action from the portal or by you from the dashboard or API), only one event is sent immediately, because the subscription stays `active` until the period ends:

1. `subscription.updated`

The `pause_at_period_end` flag is set to `true`, and `resumes_at` holds the scheduled resume date if you set one.

When the end of the current billing period arrives, the pause takes effect: billing stops and benefits are revoked. The following events are then sent:

2. `subscription.updated`
3. `subscription.paused`

Both events contain the same subscription data, now with the `paused` status.

**Resume**

When a paused subscription resumes, either immediately when you resume it or automatically on its `resumes_at` date, a new billing period starts and the customer is charged right away. The following events are sent:

1. `subscription.updated`
2. `subscription.resumed`
3. `order.created`

The subscription data reflects the new period through `current_period_start` and `current_period_end`, and the order represents the immediate charge for the new cycle.

#### Migration sequences

When Polar takes over billing of a subscription imported from another provider, these events are sent at cutover:

- `subscription.updated`
- `subscription.migrated`
- `customer.state_changed`
- `benefit_grant.created`, for any benefits attached to the product (seat-based products grant them when seats are claimed)
- `customer.updated`, if Polar sets the copied card as the customer's default payment method

Polar enqueues `subscription.updated` before `subscription.migrated`, but delivery order isn't guaranteed.

`subscription.migrated` carries `provider` and `provider_subscription_id` so you can match the Polar subscription to the source. Polar doesn't send `subscription.created`, `subscription.active`, or `subscription.resumed` for this path. A subscription already set to cancel at the end of its period arrives with `cancel_at_period_end` set, and gets `subscription.canceled` and `subscription.revoked` when that period ends.

### Members

Members are the individuals within a team customer. These events have no dedicated reference page yet. Their payload is the `Member` object.

- `member.created`: a member is added to a customer, through the API or as the owner of a new customer.
- `member.updated`: a member's details change, such as their name or role.
- `member.deleted`: a member is removed from a customer. Their active seats are revoked.
