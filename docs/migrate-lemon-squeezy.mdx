Lemon Squeezy is [winding down payment processing on March 31, 2027](https://www.lemonsqueezy.com/blog/saying-goodbye-to-lemon-squeezy), and many of its merchants are looking at Polar as their next Merchant of Record. This page answers the questions we hear most often, so you can decide whether Polar is a good fit before you start building.

## Your existing customers

You can move your active subscriptions and customers to Polar without asking anyone to enter their card details again. It all happens under **Settings → Migrations** in Polar:

1. **Connect your Lemon Squeezy store** with an API key.
2. **Review and import your catalog.** Polar checks what can move, then imports your products, discounts and customers. Billing stays on Lemon Squeezy.
3. **Set up benefits.** Polar brings over your license keys, files and links. See [Benefits and license keys](#benefits-and-license-keys).
4. **Move saved cards.** Request the copy in Lemon Squeezy, with Polar as the destination. Lemon Squeezy copies your customers and their saved cards to Polar, and usually starts within a week.
5. **Switch subscriptions.** For each subscription you select, Polar cancels it on Lemon Squeezy and takes over billing for the next renewal.

Start by moving new sales to Polar. New customers check out on Polar, while existing subscriptions keep renewing on Lemon Squeezy until you switch them.

### Payment methods that can't move

Some saved payment methods can't be carried over from Lemon Squeezy. Customers who pay this way will need to take action before or after their subscription moves:

- **PayPal:** PayPal subscriptions can't be migrated to any provider, including Stripe Managed Payments. Customers need to start a new subscription with a supported payment method before their subscription can migrate.
- **India-issued cards:** If you move to Stripe Managed Payments, customers need to reauthorize their payment method once their subscription moves to Stripe. If you move to Polar, customers need to add a new payment method.
- **Cash App Pay and Link:** These can only be migrated to Stripe Managed Payments. If you move to Polar, customers need to add a new payment method.

We're still exploring what this will look like for your customers, but we'll make sure the experience is smooth. Their subscription stays on Lemon Squeezy until they've updated their payment method, or until the migration deadline, so you don't miss any payments.

## Benefits and license keys

When you migrate from Lemon Squeezy under **Settings → Migrations**, Polar reads what each of your products gives buyers and sets it up as [benefits](/features/benefits/introduction) on the imported products. You pick which ones to bring over, and you can edit them later from **Benefits**.

| On Lemon Squeezy | On Polar                                                                                            |
| ---------------- | --------------------------------------------------------------------------------------------------- |
| License keys     | [License key benefit](/features/benefits/license-keys), with the same activation limit and expiry |
| Files            | [File downloads benefit](/features/benefits/file-downloads), with the files copied to Polar        |
| Links            | [Custom benefit](/features/benefits/custom), with the links in its note                            |

### Who gets them, and when

- **Subscribers** get the benefits when their subscription switches to Polar.
- **Past one-time buyers** get them as soon as you set up benefits. This covers paid and partly refunded orders. Polar doesn't email them: they find their keys and files in the customer portal.

### Customers keep their license key

Each customer keeps the license key they already have, with the same value. Devices stay activated too: Polar keeps each Lemon Squeezy activation under the same ID, so the `instance_id` your app saved works as the `activation_id` on Polar.

A few things don't carry over:

- **Usage and validation counts** start at zero.
- **Expiry dates** restart for one-time keys: a key that lasts a year lasts a year from the day it moves. Subscription keys don't expire on their own; they follow the subscription.
- **Keys that are disabled or expired** on Lemon Squeezy aren't brought over. A subscriber gets a new key when they switch.
- **A key whose value is already used** in your Polar organization is replaced with a new key.
- **Devices activated on Lemon Squeezy after the move** aren't on Polar. They activate once on Polar.

### Update your app before you switch

A subscriber's key only reaches Polar when their subscription switches, so for a while some keys are on Lemon Squeezy and others on Polar. Before you switch any subscriptions, ship an app update that checks the key with Polar first, and asks Lemon Squeezy only when Polar doesn't know the key yet:

```ts
// Polar knows these keys, but no longer accepts them. Don't ask Lemon Squeezy.
const REJECTED_ON_POLAR = [
  "License key is no longer active.",
  "License key has expired.",
];

async function validateOnPolar(key: string, activationId?: string) {
  const response = await fetch(
    "https://api.polar.sh/v1/customer-portal/license-keys/validate",
    {
      method: "POST",
      headers: { "Content-Type": "application/json" },
      body: JSON.stringify({
        key,
        organization_id: POLAR_ORGANIZATION_ID,
        ...(activationId && { activation_id: activationId }),
      }),
    },
  );
  if (response.status !== 200 && response.status !== 404) {
    throw new Error("Couldn't reach Polar"); // Handle it as you do today.
  }
  const body = await response.json();
  return {
    found: response.status === 200,
    granted: body.status === "granted",
    rejected: REJECTED_ON_POLAR.includes(body.detail),
  };
}

async function checkLicense(key: string, instanceId: string) {
  const device = await validateOnPolar(key, instanceId);
  if (device.found) return device.granted ? "valid" : "invalid";
  if (device.rejected) return "invalid";

  // Polar may have the key but not this device.
  const keyOnly = await validateOnPolar(key);
  if (keyOnly.found) return keyOnly.granted ? "activate_on_polar" : "invalid";
  if (keyOnly.rejected) return "invalid";

  // Polar doesn't have this key yet: ask Lemon Squeezy, as your app does today.
  const lemonSqueezy = await fetch(
    "https://api.lemonsqueezy.com/v1/licenses/validate",
    {
      method: "POST",
      headers: { Accept: "application/json" },
      body: new URLSearchParams({ license_key: key, instance_id: instanceId }),
    },
  );
  return (await lemonSqueezy.json()).valid === true ? "valid" : "invalid";
}
```

The same saved ID works with both. Polar answers 404 both when it doesn't know a key and when it knows the key but no longer accepts it, so the `detail` tells them apart. Never fall back to Lemon Squeezy for a key Polar rejected: after a refund or a revoke on Polar, the key often still works on Lemon Squeezy.

| Situation | Polar answers | Your app |
| --- | --- | --- |
| Key moved, device activated before the move | `200`, `status: "granted"` | Valid. |
| Key moved, device activated on Lemon Squeezy after the move | `404` with the device ID, `200` without it | Activate the device on Polar. |
| Key revoked or disabled on Polar | `404`, `License key is no longer active.` | Invalid. Don't ask Lemon Squeezy. |
| Key expired on Polar | `404`, `License key has expired.` | Invalid. Don't ask Lemon Squeezy. |
| Key not on Polar yet, such as a subscriber before the switch | `404`, `Not found` | Ask Lemon Squeezy. |
| Polar can't be reached | Network error or `5xx` | Handle it as an outage, not an invalid key. |

Once a key is on Polar, Polar decides. Disabling the key or letting it expire on Lemon Squeezy afterwards doesn't change Polar's answer.

Keep in mind:

- **Ship the update early.** Polar cancels the Lemon Squeezy subscription when it switches, so an app version that only checks Lemon Squeezy can't rely on that key afterwards.
- **New activations go to Polar.** When `checkLicense` returns `activate_on_polar`, or a device isn't activated anywhere yet and Polar knows the key, [activate it on Polar](/features/benefits/license-keys#activate-license-keys-optional) and save the new ID.
- **Remove the fallback** once every subscription has switched and Lemon Squeezy has stopped processing payments.

For new sales, Polar's [license key benefit](/features/benefits/license-keys) issues keys automatically after purchase, with optional activation limits and expiration.

## What you can sell

Polar is built for software and digital products: SaaS, apps, plugins, templates, courses, premium content and similar. Some categories aren't supported, such as physical goods and human services, and others need a closer look before approval. Our [Acceptable Use Policy](/merchant-of-record/acceptable-use/introduction) explains what is and isn't allowed.

## PayPal

Lemon Squeezy offers PayPal at checkout, and Polar doesn't yet. We know this is a gap for many of you, and it's on our radar, but we can't share a timeline. Polar does support cards, Apple Pay, Google Pay and a growing set of local payment methods. See [Payment Methods](/features/checkout/payment-methods) for what your customers can use today.

Keep in mind that PayPal subscriptions can't be exported from Lemon Squeezy, whichever provider you move to. Those customers will need to check out again on your new provider. See [Payment methods that can't move](#payment-methods-that-cant-move).

## Supported countries

You can sign up as an individual or as a registered company. Check the list of [supported countries](/merchant-of-record/supported-countries) to see whether we can pay out to your country and what you need to set up a payout account.

## Fees

The free Starter plan charges 5% + 50¢ per transaction. If you sell more, the Pro ($20/mo, 3.8% + 40¢), Growth ($100/mo, 3.6% + 35¢) and Scale ($400/mo, 3.4% + 30¢) plans lower your rate in exchange for a monthly fee. You can switch plans at any time. Cards issued outside the US add 1.5%.

Payouts go through Stripe with no markup from Polar: $2 per month with active payouts, 0.25% + $0.25 per payout, and between 0.25% and 1% for currency conversion depending on your country.

The [pricing page](https://polar.sh/resources/pricing) has the full breakdown, including a worked example and the sales volume at which each paid plan pays off. See [Fees](/merchant-of-record/fees) for refunds, disputes and payouts in more detail.

## What you can do today

If you want to poke around first, you can create an account in our [sandbox environment](/integrate/sandbox). It's fully isolated from production, so you can set up products, try checkout with test cards and see what Polar can do without moving any real money.

## Safety rules

- Never expose, print, log, or commit Lemon Squeezy or Polar secrets.
- Never ask the user to paste secrets into chat.
- Never handle raw card data.
- Never cancel or pause a Lemon Squeezy subscription, or create the matching
  Polar subscription, outside Polar's switch. Refuse DIY cutover scripts.
- Never issue new license keys to existing customers, and never import keys or
  activations yourself. Polar's migration keeps each customer's key and its
  activations, under the same IDs.
- Never create Polar orders for Lemon Squeezy purchases. Historical orders stay
  on Lemon Squeezy; Polar gives past one-time buyers their benefits through
  its Benefits step.
- Ask Lemon Squeezy only when Polar doesn't know the key. Polar answers 404
  both for an unknown key and for a key it no longer accepts (its `detail`
  says "License key is no longer active." or "License key has expired.").
  Never fall back for a key Polar rejected: after a refund or revoke on Polar,
  the key often still works on Lemon Squeezy.
- Any error other than 404 from Polar is an outage, not an invalid key:
  handle it the way the application already handles a provider outage.
- Never remove the Lemon Squeezy fallback before every subscription has
  switched and Lemon Squeezy has stopped processing payments.
- Never treat webhooks as exactly-once delivery. Verify signatures, persist
  the Standard Webhooks `webhook-id`, and make handlers idempotent.
- Never use email as the durable cross-system identity.
- Never overwrite a Polar Customer `external_id`. It is unique within an
  organization and cannot be changed once set.
- PayPal subscriptions cannot be moved. Those customers check out again on
  Polar. Direct other payment method questions to the migration guide.

## Phase 1: discover the current integration

Inspect and report:

- Framework, language, package manager, apps, and deployment boundaries,
  including desktop apps, plugins, or CLIs that ship to customers
- Authentication and the canonical user, account, or team ID
- Lemon Squeezy checkout, customer portal, webhook, subscription, order, and
  license key code
- Every place that calls Lemon Squeezy's license API (`activate`, `validate`,
  `deactivate`): where it runs, what it stores (key, `instance_id`), how it
  caches results, and how it behaves offline or when the API is down
- How the application delivers files and links to buyers
- Database tables that store Lemon Squeezy IDs or billing state
- How the application grants and revokes access
- Which shipped app versions are still in use and how fast customers update

Ask only what the repository cannot answer.

## Phase 2: define the identity contract

Use the application's immutable billable-customer ID as the Polar Customer
`external_id`. For new checkouts, pass it as `external_customer_id`.

Polar's catalog import creates or reuses a Polar Customer per Lemon Squeezy
customer, matched by email. Polar cannot infer the application's own customer
ID. If the application needs that mapping, match imported customers once using
an exact, unique email, then set the application's canonical ID as the Polar
Customer `external_id`. Require review for missing, duplicate, or changed
emails.

Map every Lemon Squeezy variant the application references to the imported
Polar product. Verify the mapping by interval, currency, and amount. Never join
catalogs by name alone.

## Phase 3: update license key checks

Design one function the whole application uses to check a key:

1. Validate with Polar's customer portal endpoint
   (`/v1/customer-portal/license-keys/validate`), sending the key, the Polar
   organization ID, and the saved Lemon Squeezy `instance_id` as
   `activation_id`.
2. On a Polar 404, read `detail`. If Polar rejected the key (no longer
   active, or expired), the key is invalid. Otherwise validate again without
   `activation_id`: if Polar answers 200, the key is on Polar but this device
   is not, so activate it on Polar. Only if Polar still doesn't know the key,
   validate with Lemon Squeezy as the application does today.
3. Activate a device that has no activation yet on Polar when Polar knows the
   key, and on Lemon Squeezy otherwise. Store the returned ID the same way the
   application stores `instance_id` today.
4. Record which provider answered, so the team can see when Lemon Squeezy stops
   being used.

Plan to ship this before switching any subscriptions: a subscriber's key only
reaches Polar at their switch, and Polar cancels the Lemon Squeezy subscription
when it switches.

## Phase 4: plan new sales and webhooks

- Route new checkouts to Polar with `external_customer_id`.
- Grant access from Polar webhooks and the Customer state API, with the
  current event names from the docs.
- Keep Lemon Squeezy webhooks working for subscriptions that haven't switched.
- Record exactly one billing system per subscription, and update it when a
  subscription switches.

## Phase 5: define cleanup gates

Do not delete Lemon Squeezy code because the first batch switched. Require:

- No new Lemon Squeezy checkouts
- Every subscription switched, or moved to a new Polar checkout
- License key checks answered by Polar for the shipped app versions that matter
- Both providers' webhooks understood until the last switch
- Support able to find transactions from either era
- Lemon Squeezy history retained for accounting
- Credentials revoked only after the final check

## Required output

Return:

1. Current architecture with file paths
2. Unknowns and blockers
3. Identity and catalog maps
4. License key check design, with every call site it replaces
5. Endpoint plan with verified reference and purpose
6. Webhook plan with idempotency and recovery
7. Phased implementation, shipping order, and cleanup gates
8. Schema changes, backfills, and rollback
9. Testing: unit, sandbox, and the license key fallback in both directions
10. Risks: double billing, lost access, keys that stop validating, stale app
    versions, and premature cleanup

Label every recommendation as:

- **Observed** in this repository
- **Documented** in current Polar docs or SDK types
- **Proposed**

End with the smallest safe implementation slice. Wait for approval before
editing code or changing billing state.
