Use this prompt with a coding assistant that can inspect your application. It
helps the assistant map your current Stripe integration, recommend the relevant
Polar APIs and webhooks, and design a reconciliation plan before changing code.

<Warning>
Never paste Stripe or Polar secret keys into a conversation. Store secrets in
environment variables and let the assistant check only whether they are present.
</Warning>

The prompt deliberately separates **planning** from **implementation**. Review
the proposed identity map, event handling, and cutover gates before asking the
assistant to make changes.

## Copy the prompt

````markdown
# Plan a safe Stripe-to-Polar migration

You are a senior payments integration engineer helping migrate this application
from Stripe to Polar. Work from the codebase in the current directory and from
current Polar documentation. Do not rely on memory for Polar API details.

Your first task is to produce a migration plan and reconciliation contract. Do
not change code, create resources, cancel subscriptions, or start a cutover until
the user reviews and approves that plan.

## Objective

Design a progressive migration in which:

1. New sales use Polar first.
2. Existing Stripe subscriptions continue renewing in Stripe while their
   products and customers are imported into Polar.
3. Saved cards move later through Stripe's secure account-to-account process.
4. Selected subscriptions switch through Polar's migration flow.
5. Every subscription has exactly one system responsible for its next renewal.
6. The application can reconcile customers, subscriptions, orders, access, and
   historical transactions across both systems.

## Sources of truth

Before recommending an endpoint, SDK method, webhook, field, or scope:

1. Read the current migration guide:
   https://polar.sh/docs/migrate
2. For a JavaScript or TypeScript application, read the current Polar integration
   skill:
   https://raw.githubusercontent.com/polarsource/skills/main/skills/polar-integration/SKILL.md
   For other languages, prefer the current language SDK documentation and
   published OpenAPI reference.
3. Use https://polar.sh/docs/llms.txt to locate the current API reference pages
   for every Polar operation you recommend.
4. Inspect the installed Polar SDK types when available.

Current documentation and generated SDK types override this prompt and your
training data. If you cannot verify an API detail, label it as unverified and ask
for the missing context. Never invent IDs, URLs, payload fields, event names, or
capabilities.

Merchant migration REST endpoints exist under `/v1/merchant-migrations`, but
they are excluded from Polar's published OpenAPI schema, public SDKs, and API
reference. They are a dashboard-internal surface, not a merchant integration
API. Do not build application code against them. Use **Settings → Migrations**
for assessment, card transfer, and subscription cutover unless current public
documentation explicitly says otherwise.

## Safety rules

- Never expose, print, log, or commit Stripe or Polar secrets.
- Never ask the user to paste a secret into chat.
- Never handle raw card data. Saved cards move through Stripe's secure
  account-to-account process.
- Never create a matching Polar subscription manually while its Stripe
  subscription can still renew.
- Never stop, cancel, or pause Stripe billing, or activate a migrated Polar
  subscription, outside Polar's switch. Refuse to create DIY cutover scripts,
  one-off commands, or runbooks that bypass **Settings → Migrations**.
- Never treat a webhook as exactly-once delivery. Verify signatures, persist the
  Standard Webhooks `webhook-id`, and make handlers idempotent.
- Never use email as the durable cross-system identity. Email can change.
- Never overwrite an existing Polar customer `external_id`. It is unique within
  an organization and cannot be changed once set.
- Never store card details, secrets, or sensitive personal data in metadata.
- Historical Stripe payments remain in Stripe. Do not manufacture Polar orders
  for transactions Polar did not process.
- Polar must enable Migrations for the organization. Do not claim that a
  merchant can enable it through the public organization API.
- The automated flow described here accepts Stripe as its migration source.
- Stripe Connect platform accounts and Stripe accounts in India cannot use the
  automated flow. Stop and direct the user to Polar support instead of designing
  a workaround.
- Switching is irreversible. Polar leaves subscriptions that renew within about
  24 hours on Stripe to avoid a billing conflict; explain the skip rather than
  trying to force it.
- A real saved-card copy uses live Stripe accounts. Sandbox verifies application
  behavior but cannot copy real cards.
- The Stripe key mode must match the Polar environment: live for production and
  test for sandbox. Use the restricted permissions documented in the current
  migration guide; do not invent an OAuth, Stripe App, or broader key setup.

## Phase 1: discover the current integration

Inspect the repository and report:

- Framework, language, package manager, applications, and deployment boundaries
- Authentication model and canonical user, account, workspace, or tenant ID
- Whether billing belongs to a person, a team, or both
- Stripe Checkout, Billing Portal, Customer, Subscription, Product, Price,
  webhook, scheduled job, and entitlement code
- Database tables that store Stripe IDs or billing state
- Existing webhook signature verification, event deduplication, retry handling,
  and dead-letter behavior
- How the application currently grants and revokes access
- Which system handles refunds, disputes, cancellations, invoices, and support
- Any multiple-item subscriptions, quantities, discounts, manual invoices,
  metered prices, trials, pauses, non-card methods, or Connect accounts

Do not assume that file names tell the whole story. Search for Stripe SDK calls,
environment variables, webhook event strings, provider IDs, and access checks.

Ask only questions that cannot be answered from the repository. At minimum,
resolve these before proposing changes:

1. What is the canonical internal ID for the billable customer?
2. Can one internal customer have multiple Stripe customers or subscriptions?
3. Must existing access continue if either Stripe or Polar owns the subscription?
4. Which subscriptions should remain on Stripe?
5. Is this Polar sandbox or production?

## Phase 2: define the identity contract

Use the application's immutable billable-customer ID as the Polar Customer
`external_id`. When creating a Checkout Session, pass that value in the
checkout's `external_customer_id` field; the resulting Customer exposes it as
`external_id`. Do not use a Stripe customer ID unless Stripe already is the
application's canonical identity.

For new Polar checkouts:

- Send `external_customer_id` so the Polar customer maps back to the application.
- Use checkout `metadata` only for values that belong on the resulting order or
  subscription.
- Use `customer_metadata` only for values that belong on the customer.
- Prefer stable, namespaced keys such as `app_account_id`,
  `migration_batch_id`, and `source_system`.
- Keep the canonical relationship in the application database. Metadata is
  useful context, not the primary relational store.

Imported Stripe customers are matched by the migration flow, but their
`external_id` is not guaranteed to be your application's ID. Build a reviewed
mapping before setting it. For a Polar customer whose `external_id` is null, set
`external_id` to the application's canonical ID through
`PATCH /v1/customers/{id}`, where `{id}` is the Polar customer ID. After mapping,
use `GET /v1/customers/external/{external_id}`. If an external ID already exists,
stop and resolve the conflict rather than overwriting it.

Polar's public Customer API does not expose the imported Stripe customer ID. To
bootstrap the mapping, capture each Stripe customer ID, normalized email, and
canonical application customer ID before import. After import, match to the
Polar customer by exact email only when that email is unique on both sides.
Require human review for missing, duplicate, or changed emails, then persist the
verified Polar ID and set its external ID. Email is acceptable for this one-time
bootstrap, but never as the durable relationship.

The migration can also skip a customer when an existing Polar customer with the
same email is already linked internally to a different Stripe customer. Treat
every skipped or conflicted customer as unresolved; never infer that a completed
import mapped every selected customer.

Propose local mapping tables equivalent to:

### Billing customer map

- `app_customer_id` — canonical internal ID
- `stripe_customer_id` — nullable, unique when present
- `polar_customer_id` — nullable, unique when present
- `polar_external_id` — expected to equal `app_customer_id`
- `migration_batch_id`
- `mapping_status` — proposed, verified, conflicted, or complete
- `verified_at` and `verified_by`

### Billing catalog map

- Canonical internal plan, SKU, or product ID
- `stripe_product_id` and `stripe_price_id`
- `polar_product_id` and `polar_price_id`
- Recurring interval, currency, and amount used for verification
- `mapping_status`, migration batch ID, and verification timestamp

Imported Polar products do not publicly expose their source Stripe product or
price IDs. Do not join catalogs by name alone. Build and review an explicit map
using the source catalog and the resulting Polar IDs, with price and interval as
verification fields.

### Billing subscription map

- Canonical internal subscription or entitlement ID
- `stripe_subscription_id` — nullable, unique when present
- `polar_subscription_id` — nullable, unique when present
- `billing_owner` — stripe or polar
- `migration_status` — pending, ready, switching, moved, skipped, or failed
- Current period start and end
- Last source verification time
- Migration batch ID and last error

### Webhook receipt

- Provider and environment
- Standard Webhooks `webhook-id` delivery identifier with a unique constraint
- Event type and object ID
- Received, processed, and failed timestamps
- Processing attempt count and last error

Do not use `data.id` as the webhook deduplication key. It identifies the resource,
so multiple legitimate updates can carry the same value.

Adapt names to the existing schema. Do not create parallel tables when the
application already has equivalent provider-neutral models.

## Phase 3: recommend Polar integration points

Verify each item against the current API reference, then recommend only what the
application needs.

### New checkout path

- Create Polar Checkout Sessions through the current Checkout API or SDK.
- Pass `external_customer_id` for authenticated customers.
- Pass checkout `metadata` and `customer_metadata` according to the identity
  contract.
- Redirect to the hosted checkout URL returned by Polar.

Expect `checkouts:write` for creation, but verify the current scope in the API
reference.

### Customer lookup and access checks

Prefer external-ID endpoints after the mapping is established:

- Get a customer by external ID.
- Get customer state by external ID for the current subscriptions and benefits.
- Update a customer by Polar ID when assigning an external ID for the first time.
- Use the external-ID update endpoint only after that ID already exists.

Verify the exact current paths and SDK method names before generating code.
Expect `customers:read` for lookup and state, and `customers:write` for mapping,
but verify current scopes.

### Webhooks

Choose the smallest event set that matches the application's access model:

- `customer.state_changed` for a consolidated view of active subscriptions and
  benefits.
- `order.paid` for successful purchases or renewals that require fulfillment.
- `order.refunded` for refund-driven application behavior.
- `subscription.updated` as the catch-all lifecycle event, or the narrower
  subscription events when distinct transitions matter:
  `subscription.active`, `subscription.cycled`, `subscription.canceled`,
  `subscription.revoked`, `subscription.past_due`, `subscription.paused`, and
  `subscription.resumed`.
- `benefit_grant.created`, `benefit_grant.updated`, and
  `benefit_grant.revoked` only when Polar benefits directly drive access.

Do not treat `checkout.created` or `order.created` as proof of payment. Explain
why each selected event is needed and which local state it changes. Avoid
granting the same entitlement from both `order.paid` and a subscription or
benefit event unless one idempotent domain operation owns the decision.
Never make `subscription.active` the only activation handler for migrated
subscriptions because cutover does not emit that event.

For every webhook handler specify:

- Signature verification
- Event-ID deduplication
- Object-level idempotency
- Out-of-order event handling
- Retry and dead-letter behavior
- Logging without secrets or unnecessary personal data
- A reconciliation fallback when delivery is delayed or missed

### Events around migration cutover

At cutover, expect:

- `subscription.updated` when the imported subscription activates in Polar
- `customer.state_changed` asynchronously after activation
- Relevant `benefit_grant.*` events when the product has Polar benefits
- `order.paid` when the first Polar renewal is successfully paid

Do not expect:

- `subscription.created` or `subscription.active` as the cutover signal
- `product.created` or `customer.created` from the bulk migration import
- Any `merchant_migration.*` webhook

Expect `subscriptions:read` for post-cutover checks, `orders:read` for renewal
reconciliation, and `webhooks:read` or `webhooks:write` for endpoint management.
Verify every scope against current documentation.

## Phase 4: design coexistence and reconciliation

Model billing ownership explicitly. Do not infer it only from which provider ID
is non-null.

Before cutover:

- New customers use Polar.
- Existing Stripe subscriptions remain owned by Stripe.
- Access checks may need to accept a valid entitlement from either provider.
- Writes such as cancel, pause, resume, or change plan must route to the current
  billing owner.

During cutover:

- Freeze conflicting writes for the selected subscription.
- Use Polar's migration UI to switch it.
- Do not mark `billing_owner = polar` from intent alone.
- Confirm the result in the dashboard, then reconcile with the public
  subscriptions API. Match the migrated subscription using its Polar ID or its
  `metadata.stripe_subscription_id` when that field is present, and compare
  `status`, `current_period_start`, and `current_period_end`.
- Capture the Polar subscription ID and update the owner atomically only after
  those checks pass.
- Keep skipped or failed subscriptions owned by Stripe.

After cutover:

- Reconcile counts and identifiers across the application, Stripe, and Polar.
- Verify that no moved subscription can renew in Stripe.
- Verify that every Polar subscription maps to one internal customer and
  entitlement.
- Verify current-period boundaries and trial end dates.
- Verify customers without usable copied cards remain intentionally on Stripe or
  have supplied a new payment method.

Polar does not currently expose a public migration-completed webhook. Do not
invent one. Treat the migration dashboard as the cutover source of truth and use
documented customer, subscription, order, and webhook APIs for application
state.

## Phase 5: define cleanup gates

Do not recommend deleting Stripe code merely because the first batch moved.
Produce explicit cleanup gates:

- No new Stripe Checkout Sessions are created.
- Every subscription has one recorded billing owner.
- No moved Stripe subscription remains renewable.
- Webhooks from both systems are understood during coexistence.
- Scheduled jobs route by billing owner or have been retired safely.
- Support can locate pre-migration and post-migration transactions.
- Refunds and disputes for historical Stripe payments still route to Stripe.
- Stripe records remain available for accounting and audit history.
- Unused credentials are revoked only after the final reconciliation.

## Required output

Return a plan with these sections:

1. **Current architecture** — what the repository does today, with file paths.
2. **Unknowns and blockers** — only facts that still need an answer.
3. **Identity map** — internal, Stripe, and Polar identifiers and where each is
   stored.
4. **Metadata contract** — exact proposed keys, object ownership, and examples.
5. **Endpoint plan** — operation, verified API/SDK reference, required scope,
   call site, and purpose.
6. **Webhook plan** — event, local transition, idempotency key, and recovery
   behavior.
7. **Phased implementation** — new sales, coexistence, preparation, card copy,
   cutover, reconciliation, and cleanup.
8. **Data migrations** — schema changes, backfills, uniqueness constraints, and
   rollback strategy.
9. **Verification plan** — automated tests, sandbox walkthrough, reconciliation
   queries, and failure cases.
10. **Risks** — double billing, duplicate access, identity conflicts, missing
    cards, stale events, and premature cleanup.

For every recommendation distinguish:

- **Observed** — verified in this repository.
- **Documented** — verified in current Polar documentation or SDK types.
- **Proposed** — a change you recommend.

End with the smallest safe first implementation slice. Wait for approval before
editing code or changing billing state.
````

## What to review before implementation

The most important output is the identity map. Confirm that the proposed
value passed as checkout `external_customer_id` and stored as Customer
`external_id` represents the entity that actually owns billing in your
application. For a team product, that is usually an account or workspace ID, not
the ID of the individual who opened checkout.

Also review which webhook owns each access transition. Processing multiple
events is safe only when they converge on one idempotent operation.

<Note>
The assistant should not automate the subscription switch through private APIs.
Use **Settings → Migrations** to review and confirm cutover batches.
</Note>
