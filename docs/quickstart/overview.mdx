In this quickstart you'll build a complete usage-based billing integration. You'll follow the same path as data through Polar: usage first, then pricing, then customers buying and your application reacting.

## What you'll build

- Usage events flowing from your application into a meter
- A subscription product with a base fee, metered usage and included credits
- A checkout that links each purchase to the user in your application
- A webhook handler that keeps your application in sync with each customer's access

## Prerequisites

- **A sandbox organization.** Sign up at [sandbox.polar.sh](https://sandbox.polar.sh/start). The [sandbox](/integrate/sandbox) is fully isolated from production, so nothing here moves real money.
- **An organization access token** from the sandbox, created under **Settings → Access Tokens**. See [Organization access tokens](/integrate/oat).
- **The [TypeScript SDK](/integrate/sdk/typescript), the [Python SDK](/integrate/sdk/python) or any HTTP client.** Every example has a tab for each.

<CodeGroup>
```bash TypeScript
npm install @polar-sh/sdk
```

```bash Python
pip install polar-sdk
```

```bash cURL
# Requires jq to read IDs from responses
export POLAR_ACCESS_TOKEN="polar_oat_..."
```
</CodeGroup>

Every example uses this client:

<CodeGroup>
```typescript TypeScript
import { createPolar } from "@polar-sh/sdk/2026-10";

export const polar = createPolar({
  accessToken: process.env.POLAR_ACCESS_TOKEN!,
  environment: "sandbox",
});
```

```python Python
import os

from polar.v2026_10 import Polar

polar = Polar(
    os.environ["POLAR_ACCESS_TOKEN"],
    environment="sandbox",
)
```

```bash cURL
# Every request goes to the sandbox API, pinned to API version 2026-10
curl https://sandbox-api.polar.sh/v1/... \
  -H "Authorization: Bearer $POLAR_ACCESS_TOKEN" \
  -H "Polar-Version: 2026-10"
```
</CodeGroup>

<Visibility for="agents">
  Rules for implementing this quickstart in a user's project:

  - Use the sandbox (`https://sandbox-api.polar.sh`, `environment: "sandbox"`) until the user says to go live.
  - Keep `POLAR_ACCESS_TOKEN` and `POLAR_WEBHOOK_SECRET` on the server. Never send them to the browser.
  - Use the application's own user ID as `external_id` and `external_customer_id`. Don't store Polar customer IDs.
  - Ask the user which feature to meter and how to price it. The names and amounts in these pages are examples.
  - Pin one API version across the project: `@polar-sh/sdk/2026-10`, `polar.v2026_10` or the `Polar-Version: 2026-10` header.
  - Follow the steps in order: [track usage](/quickstart/track-usage), [catalog](/quickstart/catalog), [checkout](/quickstart/checkout), [webhooks](/quickstart/webhooks). Each step ends with a way to verify it works.
</Visibility>


<Tip>
  Prefer to let your agent do it? Run `polar agent setup` to connect Claude Code, Codex or Cursor to Polar, then ask it to follow this quickstart. See [MCP](/integrate/mcp).
</Tip>

<Info>
  **Use your own user IDs.** Every Polar customer can carry an `external_id`, set to the user's ID in your application. The quickstart uses `user_123` this way throughout, so you never store Polar's customer IDs or map them back to your users. See [External IDs](/integrate/external-ids).
</Info>

## Why usage comes first

Events are raw facts about what customers do in your product. Polar stores every event and computes usage from them when you ask, so:

- You can start sending events **before** you've settled on pricing, and decide later what to charge for, if anything.
- Events sent with your own user ID are linked to the customer as soon as a customer with that external ID exists, even if the events came first.
- New meters work on events you've already sent, so you see real usage the moment you create them.

The sooner events flow, the more real data you have when you set your prices.
