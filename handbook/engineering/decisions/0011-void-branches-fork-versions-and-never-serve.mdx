title: "ADR-0011: Void branches fork a version and never serve traffic"
description: "A branch is a named, mutable patch pinned to one deployed version. It re-enters the lineage only by being promoted, which deploys its resolved configuration as an ordinary draft."
---

<Info>
**Status**: Accepted

**Area**: Cross-cutting

**Date**: 2026-09-16
</Info>

## Context

[ADR-0010](/engineering/decisions/0010-void-deployments-are-hash-versioned-and-linear)
made versions immutable and the deployment list linear: code pushes a configuration, the
server hashes it, and one deployment row per hash carries draft, active or archived. The
dashboard's simulate view wants to take one of those versions, change prices and terms,
and compare outcomes before anything is pushed. Doing that against the deployment table
would either mutate a hashed version or reintroduce a second identity next to the hash.

## Decision

A branch is a row in `void_branches` holding a name, a patch and a pointer to the deployment
it forks. It is pinned to that base version and does not follow the active version. Its
configuration is resolved on read by applying the patch to the base deployment's stored
configuration, and its hash is the version it would become. A branch has no meter or product
rows and can never be active. Promoting a branch runs the normal deploy path on the resolved
configuration, producing a draft deployment; activation stays a separate, gated step.

## Consequences

- Deployments now store their normalized configuration (`void_deployments.configuration`),
  so a version can be forked without reconstructing it from rows. Versions deployed before
  this column exists cannot be branched until pushed again.
- The version lineage stays exactly as ADR-0010 describes; branches are provenance on the
  side. A branch records the deployment it was last promoted to, and reports whether a
  deployment with its resolved hash already exists.
- Product and subscription mapping between a version and its branch is derived by slug
  and by the product a subscription pins, never stored.
- The patch is a configuration-level diff keyed by slug. Today it covers product price,
  name, description, per-meter terms and meter unit amounts; it grows with the config.
- Branches are persistent until deleted. There is no expiry.
- Known deviation from [ADR-0007](/engineering/decisions/0007-no-default-in-output-schemas):
  the branch response embeds the input-shaped patch and resolved configuration, whose
  fields carry defaults. Accepted while the Void API is excluded from the public schema.

## Alternatives considered

- **Branch as a mutable draft deployment**: breaks the hash identity and the
  "one row per version" rule of ADR-0010.
- **Storing the resolved configuration on the branch**: duplicates the base and drifts
  when the patch changes; resolving on read keeps one source of truth.
- **Expiring branches by default**: nothing about storage requires it and a lost
  experiment is worse than a stale row.
