## Context

[ADR-0010](/engineering/decisions/0010-void-deployments-are-hash-versioned-and-linear)
made versions immutable and the deployment list linear: code pushes a configuration, the
server hashes it, and one deployment row per hash carries draft, active or archived. The
dashboard's Simulate view wants to take one of those versions, change prices and terms,
and compare outcomes before anything is pushed. Doing that against the deployment table
would either mutate a hashed version or mint a new draft on every edit.

Void is Polar as code: the configuration lives in the developer's repository, and real
branching is git branching. Whatever the dashboard stores for Simulate must not pretend to
be a second lineage next to that.

## Decision

A scenario is a row in `void_scenarios` holding a name, a patch and a pointer to the
deployment it starts from. It is pinned to that base version and does not follow the active
version. Its configuration is resolved on read by applying the patch to the base deployment's
stored configuration, and its hash is the version it would become. A scenario has no meter or
product rows and can never be active.

Scenarios are a workspace concept, not a lineage concept. They are created, listed and edited
only from Simulate. They do not appear in the version selector or anywhere that lists the
deployment history. Promoting a scenario runs the normal deploy path on the resolved
configuration, producing a draft deployment, and the scenario also hands back that
resolved configuration so it can be committed to the repository; activation stays a
separate, gated step. The word "branch" is reserved for git.

## Consequences

- Deployments store their normalized configuration (`void_deployments.configuration`), so a
  scenario can start from a version without reconstructing it from rows. Versions deployed
  before this column exists cannot be used as a scenario base until pushed again.
- The version lineage stays exactly as ADR-0010 describes. A scenario records the deployment
  it was last promoted to, and reports whether a deployment with its resolved hash already
  exists.
- A scenario stays pinned to its base when a newer version activates. Promoting it then
  yields a version that drops the newer version's changes; the dashboard shows the base
  version so this is visible, and the resolved configuration is meant to be reviewed in
  the repository before it is pushed for real.
- Product and subscription mapping between a version and a scenario is derived by slug and
  by the product a subscription pins, never stored.
- The patch is a configuration-level diff keyed by slug. Today it covers product price,
  name, description, per-meter terms and meter unit amounts; it grows with the config.
- Simulation assumptions (customer growth, usage distribution) are not part of a scenario.
  They live in the browser; the server stores only the pricing patch.
- Scenarios persist until deleted. There is no expiry.
- Known deviation from [ADR-0007](/engineering/decisions/0007-no-default-in-output-schemas):
  the scenario response embeds the input-shaped patch and resolved configuration, whose
  fields carry defaults. Accepted while the Void API is excluded from the public schema.

## Alternatives considered

- **Scenario as a mutable draft deployment**: breaks the hash identity and the
  "one row per version" rule of ADR-0010, and pollutes the lineage on every edit.
- **Branches as a lineage concept**: the first version of this decision. Rejected because
  the only consumer is Simulate, the repository is the source of truth, and a Polar-side
  branch duplicates git without the merge semantics.
- **Storing the resolved configuration on the scenario**: duplicates the base and drifts
  when the patch changes; resolving on read keeps one source of truth.
- **Browser-only scenarios**: loses them across devices and team members, and makes
  promote impossible to audit.
