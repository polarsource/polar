---
title: "ADR-0014: AI agents are their own auth subject until a human claims them"
description: "An unclaimed agent authenticates as an Agent subject that endpoints must opt into; after the claim it acts for the user like any OAuth app."
---

<Info>
**Status**: Accepted

**Area**: Backend

**Date**: 2026-10-16
</Info>

## Context

With agent sign-up (the WorkOS auth.md spec), an AI agent can create and build an
organization before any human exists. Something has to own that org and make the API calls. A
placeholder `User` with a fake email would work, but it puts non-people in the users table and needs
guards on login, emails, metrics and every endpoint that must stay off-limits. Borrowing the
`Organization` subject avoids fake users, but endpoints can't tell an agent from an organization
access token.

## Decision

**Before the claim, an agent is an `Agent` auth subject.** Its identity is a row in one `agents` table,
created at sign-up, which also holds its OAuth client, its status and who claimed it. It authenticates
as itself, owns its org through an agent–organization link (not a `UserOrganization` membership), and
can only reach endpoints whose `Authenticator` lists `Agent` in `allowed_subjects`. **After the claim,
it acts for the claiming user with ordinary user OAuth tokens**, and its OAuth client stays marked as
an agent.

## Consequences

- New rule: to open an endpoint to unclaimed agents, add `Agent` to that module's `Authenticator`,
  handle `is_agent` in the service's subject branches, and test it with
  `@pytest.mark.auth(AuthSubjectFixture(subject="agent"))`. Check the existing `if is_user(...) else`
  branches: code that treats every non-user as an `Organization` will misread an `Agent`.
- Opt in only build endpoints (orgs, products, meters, benefits, discounts, events, config). Never opt
  in endpoints that move real money or manage members and payouts. A test pins the list of
  authenticators that accept `Agent`, so every new opt-in shows up in review.
- Unclaimed agent tokens also carry only the build scopes. The allowlist is the guard; scopes are a
  second layer, so one wrong opt-in doesn't open a money endpoint by itself.
- No placeholder users. The users table, login, emails and user metrics only ever see people.
- The org-access helpers (`get_accessible_org_ids`, `get_accessible_organization`,
  `get_payload_organization`, the authz policies) resolve an `Agent` to the orgs it owns.
- OAuth tokens gain a third sub type, `SubType.agent`, with its own access-token prefix
  (`polar_at_a_`). Agent tokens have no refresh token: the agent renews by exchanging its identity
  assertion.
- An org owned by an agent has no human owner until the claim. Code that looks up the owner must
  handle that, and the org can't go live before then.
- The claim adds the human as owner and revokes the agent's pre-claim tokens. Nothing moves between
  users.
- Trade-off: after the claim, endpoints can't tell an agent from the user it acts for by the subject
  alone; that takes the OAuth client's agent marker.

## Alternatives considered

- **Placeholder `User` with an unreachable email**: no new subject, but fake users everywhere and many
  guards to keep them in bounds.
- **Reuse the `Organization` subject** (like organization access tokens): no new subject, but agents
  aren't distinguishable from org tokens, so agent rules can't be expressed on endpoints.
- **`Agent` subject after the claim too**: every user endpoint would need to opt in for the agent to
  act for its user. Delegated user tokens already cover that.
- **Only support sign-up with a human up front (`service_auth`)**: no pre-claim identity needed, but
  agents couldn't build anything before a human is involved.
