## Summary

We want to let agents start making changes on the Polar side. Agents will write config files to create products, benefits, and meters. But we want agents to do that safely, for merchants and for customers.

To achieve that, we propose to follow some design principles:

1. Every change goes into a **draft catalog**. The merchant can publish it, then it becomes the **live catalog**. Every new checkout goes through the live catalog.
2. Every change in product, benefit, or meter gets a **new row with a new ID**. Old rows don't change, and existing orders and subscriptions continue pointing to them.
3. To change how customers are billed or to grant new benefits, merchants should create a new **migration**.

This versioning behavior is an opt-in feature that the merchants must agree to. Every new org will get this behavior from now on.

Merchants will be able to make multiple changes on the Dashboard, and those changes will be saved in a draft. Saving a draft does not affect new purchases or existing ones. Publishing a draft will make it the live catalog. Merchants will be able to inspect every catalog version and compare it to old ones.

## Current state

Today, when a merchant changes the product price on the dashboard, this applies to new subscriptions only, and old subscriptions are grandfathered on the old price. Merchants can upgrade customers to the new price using the subscription update endpoint.

Product benefit updates apply to all customers, old and new. And a meter cannot be updated once it has ingested events. Merchants need to create a new product with a new meter, or have the old and new meters on the same product, making sure that they do not overcharge customers.

## Goals

- Provide a unified approach to updating billing entities.
- Make billing changes in a safe and predictable way.
- Allow customers to be migrated to the latest versions.

## Out of scope

- Customer notifications related to billing changes (this will come later).

## Options

| Option | We pick it? |
|---|---|
| **Catalogs**: immutable rows grouped by a Catalog entity | Yes |
| **Stable ids with version tables**: the product id never changes and versions live in another table | No. Has better compatibility but we need two models for every resource |
| **One catalog version per customer** | No. Purchases made at different times can't live side by side |
| **New logical_id attribute** | No. Merchants can set external_id and logical_id that have a similar behavior |
| **No versioning**: the merchant writes `pro_v2` for external id | No way |

## Solution

There are only 4 concepts that make all of this possible:

1. **Catalog.** It contains the full list of products, meters, and benefits at a point in time. It has different states: `draft`, `live`, or `archived`. Every organization has at most one draft and one live catalog. 
2. **Copy-on-write** for products, meters, and benefits. Changes to entities cannot have an impact on existing customers; therefore, every change to a product, meter, or benefit will create a new row in a draft catalog. Once the catalog is live, the changes are locked, and no more edits can happen to those rows.
3. `external_id` is the stable name. A row is now unique by `(organization_id, external_id, version)`. `version` is the catalog where the entity was created.
4. **`is_current`.** It is `true` for rows in the live catalog. It is a fast way to filter for current entities and new sales. The list of rows in each catalog (catalog membership) is the source of truth.

### What we store

If ACME sells a Pro product at $20 and another Starter at $10 in catalog 1. Then, the merchant change Pro to $25 and publish a new catalog version. We can see that Starter didn't change so the product is reused in Catalog 2.

`catalogs`

| id | version | status |
|---|---|---|
| `cat_1` | 1 | `archived` |
| `cat_2` | 2 | `live` |

`products`

| id | external_id | version | price | is_current |
|---|---|---|---|---|
| `prod_A` | `pro` | 1 | $20 | `false` |
| `prod_B` | `pro` | 2 | $25 | `true` |
| `prod_C` | `starter` | 1 | $10 | `true` |

Catalog membership

`catalog_products`

| catalog | external_id | product |
|---|---|---|
| 1 | `pro` | `prod_A` |
| 1 | `starter` | `prod_C` |
| 2 | `pro` | `prod_B` |
| 2 | `starter` | `prod_C` |

`subscriptions`

| id | product_id | pays |
|---|---|---|
| `sub_1` (bought in catalog 1) | `prod_A` | $20, until a migration |
| `sub_2` (bought in catalog 2) | `prod_B` | $25 |

Things to notice:

- `prod_A` still exists and still costs $20. Reading `prod_A` always returns the $20 definition. An old id never redirects to the new one.
- `prod_C` was created in catalog 1 and reused in catalog 2. It keeps `version = 1`, and it is still current.
- A purchase reads its own row directly. We never search "which version does this customer have".

### What creates a new row

| Change at publication | Result |
|---|---|
| Any change to a product, including its name | New product row |
| Any change to a benefit | New benefit row, plus new rows for the products granting it |
| Any change to a meter, including its name | New meter row, plus new rows for the credit benefits and products using it |
| Same definitions applied again | No new catalog |

The review screen and the plan show all the extra rows for dependent products.

### Main flows

#### Making a change

From the dashboard the flow is: edit → save draft → review → publish.

1. The merchant opens the Pro product, changes the price to $25, and clicks Save. New sales still use $20. On the dashboard we will show that this is only in draft.
2. Another member edits another product. This change goes to the same draft.
3. The dashboard will have an option to Review the draft to see the changes.
4. And finally a member can Publish. At this point, catalog 2 goes live.

For the code, the behaviour it's the same and merchants edit the code inplace. The only difference is that any apply should have no effect on existing customers or subscriptions, only to new checkouts:

```tsx
import { defineConfig, usd } from "@polar-sh/polar"

export default defineConfig({
  meters: () => ({}),
  products: ({ product, fixed }) => ({
    pro: product("Pro").prices(fixed().amount(usd(25))).recurring("monthly"), // was usd(20)
  }),
})
```

```text
~ catalog   1 → 2
~ pro       prod_A → prod_B · price $20.00 → $25.00 · 168 subscriptions stay on prod_A
```

There are some rules:

- Entities in draft cannot be sold, they act like in an archived version, but they are editable.
- Every save should leave the draft in a complete and valid state, it should have the next Catalog version. This means that if we change a benefit, the related product should be changed also.
- If a draft exists, `apply` will raise a conflict error. The merchant should be able to force apply or to do a pull of the draft changes.
- Publishing a catalog is an atomic operation.
- There is no revert. To have the same config, the merchant should publish a new catalog with the old definition.

#### New sales
Every new checkout should only use the live catalog, identified by `is_current`:

```sql
SELECT * FROM products
WHERE organization_id = :organization_id
  AND external_id = 'pro'
  AND is_current = true;
```

Checkouts created with the old catalog should keep that pricing.

#### Removing an entity

Removing an entity from the catalog means that the entity is not in the draft catalog relationship. When publishing, we set the deleted entity to `is_current = false`.

```text
Catalog 2: pro → prod_B, starter → prod_C
Draft:                   starter → prod_C
Publish catalog 3:  prod_B.is_current = false
```

#### Migrations

A migration moves an existing customer to a new catalog version. This is a separate action from publishing, but merchants can combine publishing a nnew catalog and doing a migration.

Imagine that ACME also sells a one-time Download bundle: `prod_D`, with 2 files. Catalog 2 adds a third file, so the bundle is now `prod_E`. ACME moves everyone:

```tsx
migrations: ({ migrate }) => ({
  "catalog-2-rollout": migrate
    .customers()
    .all()
    .toCatalog(2)
    .subscriptions({ at: "next_period" })
    .oneTimeBenefits({ at: "immediate" }),
}),
```

```text
+ catalog-2-rollout   → catalog 2
  pro              168 subscriptions · prod_A → prod_B at next renewal · 168 pay more ($20.00 → $25.00)
  download-bundle   40 one-time purchases · prod_D → prod_E now · +1 file
```


We can move customers to use different products using `toProduct`:

```tsx
"starter-to-pro": migrate.subscriptionsOf("starter").allCustomers().toCatalog(2).toProduct("pro").atNextRenewal(),
```

Some rules apply:

- Products are matched by `external_id` in the target catalog.
- Merchants can decide to move subscriptions or one-time benefits.
- The list of customers is fixed when running the plan, so rerunning the apply should be idempotent.
- Two migrations on the same apply cannot target the same subscriptions or customers.
- Manual changes take priority over migrations.

**Subscriptions.** `next_period` moves each subscription on the next billing period, `immediate` needs an explicit `prorate` or `invoice` choice. Similar to today's API.

**One-time purchases.** The orders don't change, only the benefit grants can change.

**Benefits.** A migration doesn't revoke the old grant and create a new one. It keeps the grant and points it to the new benefit row. Example: the License key benefit allows 3 activations (`ben_1`). Catalog 2 allows 5 (`ben_2`):

| | Before migration | After migration |
|---|---|---|
| Grant | `grant_1` → `ben_1` | `grant_1` → `ben_2` |
| License key | `ABC-123`, 2 devices active | `ABC-123`, 2 devices active |
| Activation limit | 3 | 5 |

Some rules apply:

- If the new benefit is stricter than the grant, the migration should block it. For example, a merchant cannot move a customer with 5 devices to a new benefit that allows 3 devices.


**Meters and credits** are still open for discussion. This may be a design doc on its own. See [Open questions](#open-questions).

#### What changes for merchants

| | Today | With catalogs |
|---|---|---|
| Change a price | Old prices are archived. Existing subscriptions keep them | New product row in a new catalog. Existing subscriptions use the old product row |
| Change a benefit | Changes for all customers | New benefit row. Existing grants keep the old definition |
| Change a meter | Locked once billing starts | New meter row. Existing customers keep the old meter. How they migrate is open |
| Product id after a change | Same id | New id. `external_id` stays the same |
| Dashboard edit | Live right away | Saved in a draft. Live when the catalog is published |
| Past one-time buyers | Get benefit changes automatically | Get them only through a migration |
| Move existing customers | By hand, one by one | A migration, with a plan that shows the impact |

Opting in is one-way for now. Before activation, every product, benefit, and meter needs an `external_id`. Activation creates catalog 1 from today's state, and existing purchases keep their rows and prices.


## Open questions

1. **Meters.** How do we count, bill, and move customers who are on an old meter? What happens when two purchases share a meter? Can a meter change apply immediately?
2. **Credits.** When recurring credits change, do we apply it at the next renewal? For one-time orders, do we keep what was already issued? How do we remove credits? How do we move credits between meters?
3. **Migrations.** we need to decide which changes do we allow and which should we block. Those are mainly for benefits changes or billing changes. Some examples: should we allow to grant access to have a GitHub benefit attached to one repo and allow them to move to another Repo?
4. **Adoption.** How do we move existing orgs to versioning? Should we enforce this behaviour at some point?


## Security considerations

- **Data in and out:** config from merchants and agents, and plan reports with counts and amounts.
- **Who can access it:** the existing read and write scopes. Subscription migrations also need `subscriptions:write`. One-time migrations need their own write permission. Apply checks permissions again.
- **Data we store:** draft and published rows, catalogs, and migration records. No new personal data.
- **Risks:** an agent moves many customers to higher prices. Mitigations: plan before apply, idempotent work, and cancel of migrations.

## Appendix: Milestones

**POC goal.** Prove the core loop on one internal organization:

1. Change Pro from $20 to $25 in config.
2. `plan` shows `prod_A → prod_B`. `apply` publishes catalog 2.
3. A new checkout sells `prod_B` at $25.
4. The old subscription stays on `prod_A` at $20.
5. A migration moves it to `prod_B` at its next renewal.

## Appendix: How others do it

| Provider | When the price changes | Existing customers | How to move them |
|---|---|---|---|
| Stripe | A new price is created, the old one is deactivated | Keep the old price | By hand, or with subscription schedules |
| Orb | A new plan version is created | Stay on their version | Migrations, that can be scheduled and canceled |
| Metronome | The rate card changes from a date | Stay on their rate card | By editing each contract |
| Lago | The plan is edited in place | **Are repriced right away** | A new plan, and then a migration |
| Chargebee | Only new subscriptions get the new price | Keep the old price | A bulk update tool |
| Autumn | A new version is created, if the plan has customers | Stay on their version | Migrations from the CLI |
| `void` branch (our prototype) | The whole config gets a new version | Stay on their version | Not possible |
| **Polar today** | Old prices are archived, other fields change in place | Keep the old price, but get the other changes | By hand |
| **This design** | A new catalog with new rows for changes | Keep their rows | Explicit migrations |
